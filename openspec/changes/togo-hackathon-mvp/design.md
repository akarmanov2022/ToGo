# Design

## Context

В репозитории уже есть каркас (см. proposal.md, раздел Impact):

- `backend`: Spring Boot 4.1, Kotlin 2.2, Java 21, Maven. Подключены стартеры Web MVC, Data JPA, Flyway, Security,
  Validation и Actuator. Рабочая база — PostgreSQL 18, тесты используют её же в Testcontainers.
- `api/openapi.yaml`: контракт API, источник истины для поведения сервера и клиента. `openapi-generator`
  (`kotlin-spring`, `serviceInterface=true`) генерирует контроллеры и по одному интерфейсу сервиса на тег в пакет
  `itmo.goto.generated`. Классы, написанные вручную, например `EventsService`, реализуют эти интерфейсы.
- `backend/src/main/resources/db/migration/V1__base_structure.sql`: таблицы `users`, `categories`, `events`,
  `event_users` и `event_categories`.
- `frontend`: каркас на Vue 3, TypeScript, Vite, Pinia и TanStack Query с демонстрационными данными.
- `infra/docker-compose.yml`: контейнер PostgreSQL 18.

## Goals / Non-Goals

**Goals:**

- Реализовать контракт из `main` без расхождений, чтобы фронтенд работал на заглушках по нему же.
- Держать правила событий (лимиты, состояние, присоединение и выход) в чистом Kotlin, который тестируется без Spring и
  базы данных.
- Держать демо на публичном сервере с первых дней и обновлять его автоматически из ветки `main`.

**Non-Goals:**

- Горизонтальное масштабирование и кэширование. Из фоновой обработки нужен только переход состояний событий по срокам.
- Доступность и локализация сверх русского текста интерфейса.
- Инструменты администратора: справочник категорий меняется через миграции.
- Профиль, карта и комментарии: их нет в контракте, они вне этого изменения.

## Decisions

### 1. Контракт главный, интерфейсы сервера генерируются

Поведение задаёт `api/openapi.yaml`. Новый эндпоинт или поле сначала появляются в контракте, потом в коде. Бэкенд
реализует сгенерированные интерфейсы `*ApiService`. Фронтенд генерирует типы TypeScript из того же файла и работает на
заглушках, пока бэкенд не готов.

Эндпоинты контракта (теги в квадратных скобках):

| Метод и путь                                                         | Назначение                                     |
|----------------------------------------------------------------------|------------------------------------------------|
| `POST /api/v1/auth/telegram`                                         | [Auth] вход по initData                        |
| `GET /api/v1/users/me`                                               | [Users] текущий пользователь                   |
| `GET /api/v1/categories`                                             | [Categories] справочник                        |
| `GET /api/v1/events?query=&categoryId=&startsFrom=&startsTo=&state=&participating=&limit=&offset=` | [Events] поиск и «Мои события» |
| `POST /api/v1/events`, `GET /api/v1/events/{eventId}`, `PATCH /api/v1/events/{eventId}` | [Events] создание, карточка, изменение |
| `POST /api/v1/events/{eventId}/cancel`                               | [Events] отмена                                |
| `GET /api/v1/events/{eventId}/participants`                          | [Events] список участников                     |
| `PUT /api/v1/events/{eventId}/participants/me`, `DELETE /api/v1/events/{eventId}/participants/me` | [Events] вступить, выйти |

Ошибки возвращаются в формате `ApiError { code, message, details[] }` из контракта. `code` — стабильный машинный код:
400 VALIDATION_ERROR или CATEGORY_NOT_FOUND с ошибками полей в `details`, 401 INVALID_TELEGRAM_INIT_DATA при входе
и UNAUTHORIZED для остальных операций, 403 FORBIDDEN, 404 EVENT_NOT_FOUND, 409 REGISTRATION_CLOSED,
INVALID_EVENT_STATE, EVENT_FULL, CAPACITY_BELOW_PARTICIPANTS или ORGANIZER_CANNOT_LEAVE, 500 INTERNAL_ERROR без
внутренних деталей. Глобальный обработчик исключений и обработчики Spring Security формируют этот формат.
Неизвестные поля запросов отклоняются с 400.

Альтернатива: problem details по RFC 9457. Не выбрана, потому что контракт в `main` уже описывает `ApiError`, и клиенту
нужен стабильный код ошибки.

### 2. Автоматический вход Telegram Mini App

При запуске внутри Telegram фронтенд получает исходную строку `Telegram.WebApp.initData` и отправляет
`{ "initData": "..." }` в `POST /api/v1/auth/telegram`. Формы входа, Telegram Login Widget и выбора
демо-пользователя нет. После успеха клиент открывает приложение под пользователем Telegram.

Бэкенд проверяет данные по алгоритму Mini App:

- Разделяет query string на пары и URL-декодирует ключи и значения ровно один раз; дубли ключей отклоняются.
- Удаляет `hash`, сортирует остальные поля и собирает `key=value` с разделителем `\n`. Значение `user` до проверки
  подписи сохраняется в исходном декодированном виде, без повторной JSON-сериализации.
- Вычисляет `secretKey = HMAC_SHA256(key="WebAppData", data=botToken)`, затем
  `expectedHash = HMAC_SHA256(key=secretKey, data=dataCheckString)`; сравнивает байты подписи за постоянное время.
- Проверяет через внедрённый `Clock`, что `auth_date` не старше 5 минут и не опережает сервер более чем на 30 секунд.
- Требует подписанный `user` с корректным Telegram ID. `initDataUnsafe`, отдельно присланный ID и username
  не являются основанием для аутентификации. Любой отказ не создаёт пользователя и не выдаёт токен.

Алгоритм: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app.
Проверка — чистый компонент без Spring; тесты используют вымышленный токен бота и фиксированное время.
Токен бота берётся из `TELEGRAM_BOT_TOKEN`, не передаётся клиенту и не логируется вместе с `initData`.
После проверки сервис находит или создаёт пользователя по Telegram ID и обновляет `tg_login` из проверенного
username, записывая null при его отсутствии.

Контракт возвращает `accessToken`, `tokenType: Bearer`, `expiresIn: 3600`, `user` и заголовок
`Cache-Control: no-store`. Все последующие запросы, кроме входа, требуют `Authorization: Bearer <accessToken>`.
Spring Security проверяет подлинность и срок действия токена приложения; аутентификация через cookie,
`formLogin` и HTTP Basic не используется. CSRF для этого API отключается только при условии, что сервер
не принимает автоматически отправляемые браузером cookie как средство аутентификации.

Токен хранится клиентом в памяти. После перезагрузки клиент повторяет обмен ещё свежего `initData`;
после 401 или при просроченном `initData` очищает токен и показывает предложение переоткрыть Mini App.
Без `initData` показывает сообщение об открытии через Telegram, не форму логина.
Серверного logout и refresh в текущем контракте нет. Обсуждённая refresh-сессия — отдельное будущее изменение
контракта и хранения; этот план не обещает автоматическое продление access token.

Альтернатива: Telegram Login Widget и сессионная cookie. Не выбрана, потому что продукт запускается как Mini App
внутри Telegram и использует предоставленные Telegram подписанные данные запуска.

### 3. Один origin и запуск внутри Telegram

В разработке Vite проксирует `/api` на `localhost:8080`. На сервере сборка SPA лежит в статических ресурсах бэкенда
и отдаётся самим Spring Boot. API и клиент используют один origin.

В BotFather настраивается HTTPS-адрес Mini App и кнопка её открытия. Настоящий вход проверяется запуском
Mini App внутри Telegram по этому адресу. До появления сервера используется HTTPS-туннель.
При обычном открытии URL в браузере без данных запуска сервер не выдаёт токен.
Для разработки интерфейса MSW подменяет ответы API локально; такой режим не отключает серверную проверку
`initData` и не входит в публичную сборку. Профиль `demo` отвечает только за тестовый набор данных,
а не за вход под произвольным пользователем.

### 4. Чистые доменные правила, JPA на краю

Пакет `itmo.goto.domain` содержит Kotlin-код без фреймворков: лимиты участников, переходы состояний по сроку регистрации
и окончания из спецификации `event-participation` и правила присоединения, выхода, изменения и отмены. Эти правила
превращают запрос либо в новое состояние, либо в типизированный отказ с кодом из `ApiError`. Сервисы в
`itmo.goto.service` загружают JPA-сущности, вызывают домен и сохраняют результат. Текущее время приходит из внедрённого
`java.time.Clock`, поэтому тесты состояния фиксируют часы, а не ждут.

Альтернатива: правила внутри JPA-сущностей. Отвергнута: таблица состояний — самая рискованная логика недели, и ей нужны
быстрые юнит-тесты без поднятия контекста.

### 5. Срок регистрации и состояния события

`registrationClosesAt` — источник истины для возможности изменить состав участников.
Организатор задаёт его при создании: `now < registrationClosesAt <= startsAt < endsAt`.
`startsAt` определяет начало встречи и последнюю возможность отмены организатором, но не заменяет срок регистрации.
Все даты передаются с часовым поясом, хранятся в `timestamptz` и возвращаются в UTC.

В БД хранится `state` с пятью значениями API:

- `recruiting`: набор открыт, пока `now < registrationClosesAt`;
- `registration_closed`: срок регистрации наступил и минимум набран; состав зафиксирован, встреча ожидается или идёт;
- `cancelled_by_system`: к сроку регистрации минимум не набран;
- `cancelled_by_organizer`: организатор отменил встречу до `startsAt`;
- `finished`: у неотменённой встречи наступил `endsAt`.

При достижении минимума или заполнении мест состояние остаётся `recruiting`. Число свободных мест `availableSlots`
отображается отдельно; положительное число не даёт права вступить после срока регистрации. При
`now == registrationClosesAt` вступление и выход уже запрещены. Отменённые события не переходят в `finished` и сохраняют
участников.

Фоновая обработка закрывает набор и завершает встречи. Каждая операция над событием под блокировкой сначала
актуализирует его состояние по серверному времени, затем проверяет допустимость действия. При задержке обработки
событие не остаётся открытым: чтение карточки и поиск также возвращают актуальное состояние, а фильтр `state`
применяется к нему. Если обработка впервые произошла после `endsAt`, сначала проверяется минимум при закрытии
регистрации, затем успешное событие переводится в `finished`; недобор остаётся `cancelled_by_system`.

Альтернатива: вычислять состояние только по `startsAt` и числу участников. Не выбрана, потому что она допускает
изменение состава после заданного организатором срока и не соответствует состояниям API.

### 6. Лимит при одновременных запросах: блокировка строки события

Вступление, выход, изменение, отмена и закрытие набора выполняются в одной транзакции. Сначала она блокирует строку
события (`SELECT ... FOR UPDATE` через метод репозитория с `@Lock(PESSIMISTIC_WRITE)`), затем считывает серверное
время после получения блокировки, актуализирует состояние, считает участников в `event_users` и проверяет доменные
правила. Только затем добавляет или удаляет участие. Все изменения состава проходят через эту блокировку, поэтому
подсчёт под ней точен без денормализованного счётчика.
Если запрос ждал блокировку и получил её после дедлайна, он не меняет состав, даже если поступил раньше.
Актуализация состояния должна сохраняться и при отказе в действии: типизированный отказ возвращается из
транзакции и преобразуется в HTTP-ошибку после commit, чтобы не откатить закрытие регистрации. Повторное вступление
определяется до проверок состояния и подкреплено уникальным ограничением `(event_id, user_id)`.

Альтернатива: оптимистическая блокировка через `@Version`. Отвергнута: проигравший запрос получает общую ошибку
«повторите попытку» вместо понятного ответа EVENT_FULL, которого требует спецификация.

Альтернатива: счётчик `participant_count` в `events`. Отвергнут: в V1 его нет, а при общей блокировке он только
добавляет риск расхождения со строками участия.

### 7. Модель данных

Модель задаёт `V1__base_structure.sql` из `main`:

```
users(id uuid, tg_id bigint unique, tg_login null)
categories(id uuid, name unique)
events(id uuid, starts_at, ends_at, registration_closes_at timestamptz,
       title, description, location, state, icon null,
       min_users, max_users, organizer_id)
event_users(id uuid, event_id, user_id)          -- unique (event_id, user_id)
event_categories(id uuid, event_id, category_id) -- unique (event_id, category_id)
```

V1 не меняется. Новая миграция V2 добавляет ограничения CHECK по спецификации: `1 <= min_users <= max_users`,
`registration_closes_at <= starts_at < ends_at`, `state` из пяти значений решения 5. Проверка
`registrationClosesAt > now` выполняется сервисом при создании и изменении, а не динамическим CHECK. Индексы для
обработки сроков: `events(registration_closes_at) WHERE state = 'recruiting'` и
`events(ends_at) WHERE state = 'registration_closed'`. Та же миграция наполняет справочник категорий.

### 8. Запрос поиска

Перед выборкой сервис актуализирует события, у которых наступил срок и сохранённое состояние устарело, теми же
правилами, что и фоновая обработка. Затем один запрос репозитория собирается через JPA `Specification` из
необязательных фильтров: `lower(title)` содержит `query` без крайних пробелов, существует связь с `categoryId`,
`starts_at >= startsFrom`, `starts_at < startsTo`, `state = :state`, существует участие текущего пользователя при
`participating=true`. Сортировка `starts_at, id`, страница по `limit` и `offset`, `total` — отдельный подсчёт по тем же
условиям. Признаки `isParticipant` и `isOrganizer` вычисляются для текущего пользователя.

### 9. Стек фронтенда

Vue 3 с TypeScript на Vite, Pinia для состояния сессии, TanStack Query для запросов к API, Vue Router. Типы API
генерируются из `api/openapi.yaml` через `openapi-typescript`, обработчики MSW по контракту используются в первые дни.
Структура `src/app`, `src/modules`, `src/pages` уже есть в `main`.

Альтернатива: React. Не выбрана, потому что каркас в `main` уже на Vue.

### 10. Тесты

Доменные правила — обычные тесты JUnit 5. Репозитории и правило об одновременных запросах — `@DataJpaTest` на PostgreSQL
в Testcontainers с переиспользованием контейнера между тестами, потому что блокировка строки, `uuidv7()` и `lower()`
на другой базе ведут себя иначе. Веб-слой — срезы `@WebMvcTest` для кодов ответа и `ApiError`. Сценарий гонки
запускает два присоединения в параллельных потоках с ограничением по времени.

### 11. Демо-данные

Отдельная локация Flyway `db/demo`, включённая только в профиле `demo`, добавляет около сорока событий с разными
категориями, состояниями и датами, а также несколько демо-пользователей с выдуманными идентификаторами Telegram.
В тестах и при обычном запуске она не выполняется. Для событий задаются согласованные `registration_closes_at`,
`starts_at`, `ends_at` и `state`. Записи вымышленных пользователей нужны для наполнения событий, но не дают
возможности войти от их имени: сквозной вход показывается на настоящих аккаунтах Telegram.

### 12. Сервер: один VPS с Docker Compose

Арендуется один облачный сервер (2 vCPU, 4 ГБ памяти, Ubuntu 24.04) у провайдера, который принимает оплату команды, и
покупается домен с A-записью на IP сервера. На сервере Docker Compose по файлу `infra/docker-compose.prod.yml` запускает
три контейнера:

- `caddy` — принимает HTTPS на портах 80 и 443, сам выпускает и продлевает сертификат Let's Encrypt для домена и
  проксирует запросы в приложение (`infra/Caddyfile`);
- `app` — образ приложения с профилем `demo`; Flyway накатывает миграции при старте;
- `postgres` — PostgreSQL 18 с данными в именованном томе; наружу порт не открыт.

Секреты (`TELEGRAM_BOT_TOKEN`, `POSTGRES_PASSWORD`) лежат только в файле `.env` на сервере, рядом с compose-файлом. В
репозитории их нет, и локальный `infra/docker-compose.yml` тоже берёт пароль из переменной окружения.

Альтернативы:

- Управляемый Kubernetes. Отвергнут: за неделю его настройка не окупится, а нагрузка демо умещается в один сервер.
- Управляемая база данных. Отвергнута: лишние расходы и сетевые настройки, резервные копии демо-данных не нужны.
- PaaS вроде Render или Fly.io. Отвергнут: оплата из России ненадёжна, а вход через Telegram всё равно требует своего
  домена.

### 13. CI/CD на GitHub Actions

Многоэтапный `Dockerfile` в корне репозитория: этап Node собирает SPA, этап Maven собирает jar со сборкой SPA внутри, а
итоговый образ содержит только JRE 21 и jar.

- `.github/workflows/ci.yml` запускается на каждый запрос на слияние и на push в `main`: `./mvnw verify` для бэкенда
  (Testcontainers использует Docker раннера `ubuntu-latest`, зависимости Maven кэшируются) и `npm ci && npm run build`
  для фронтенда.
- `.github/workflows/deploy.yml` запускается после успешного CI на `main`: собирает образ, публикует его в GitHub
  Container Registry с тегом по SHA коммита, затем по SSH выполняет на сервере `docker compose pull` и
  `docker compose up -d` с этим тегом.
- Секреты GitHub: SSH-ключ деплоя, адрес и пользователь сервера. Токен бота и пароль базы в GitHub не хранятся.
- Ветка `main` защищена: слияние только через запрос на слияние с зелёным CI.
- Откат — ручной запуск `deploy.yml` (`workflow_dispatch`) с SHA предыдущего коммита.

Альтернатива: собирать образ прямо на сервере через `git pull`. Отвергнута: сборка Maven и Node нагружает маленький
сервер, а образ из реестра одинаков у CI и сервера.

## Risks / Trade-offs

- [Spring Boot 4 и опция генератора `useSpringBoot4` появились недавно, и сгенерированный код может не скомпилироваться
  для некоторых схем] → Собрать проект по контракту в первый день, чтобы проблемы генератора всплыли до того, как от них
  кто-то зависит.
- [Сгенерированные модели Kotlin не отклоняют неизвестные поля и null в PATCH] → Настроить Jackson на отказ при
  неизвестных свойствах и покрыть тестами `@WebMvcTest` ответ 400 для лишнего поля и пустого изменения.
- [Access token истёк, а старые initData больше не принимаются] → Обработать 401 без бесконечных повторов,
  очистить токен и предложить переоткрыть Mini App; refresh не считать уже реализованным.
- [Фоновое закрытие регистрации задержалось] → Проверять серверное время после блокировки и возвращать
  актуальное состояние при чтении и поиске; покрыть тестами ровно дедлайн и запрос, ожидающий блокировку.
- [Путаница с часовыми поясами в фильтрах и состоянии] → `timestamptz` в базе, `OffsetDateTime` в API, сервер отвечает
  в UTC, тесты фиксируют часы.
- [Подсчёт участников без блокировки вернёт устаревшее число] → Изменять состав только под блокировкой события;
  чтение может показать число на момент запроса, это допустимо.
- [Нет HTTPS-адреса для запуска Mini App] → Настроить адрес сервера у бота во второй день; до появления сервера
  использовать HTTPS-туннель и проверять запуск именно внутри Telegram.
- [Оплата сервера, DNS и выпуск сертификата займут дни] → Купить сервер и домен в первый день, а во второй задеплоить
  пустой каркас через пайплайн, пока на нём ничего не зависит.
- [Моки разработки попадут в демо] → Не включать MSW в публичную сборку; профиль `demo` меняет только данные
  и не разрешает обход проверки подписи Telegram.
- [Пароль базы открытым текстом в `infra/docker-compose.yml` и `application.properties`] → Перенести его в переменные
  окружения вместе с первой задачей по серверу.
- [Тесты на Testcontainers замедляют CI] → Кэшировать зависимости Maven и переиспользовать контейнер внутри одного
  запуска.
- [Токен бота утечёт в репозиторий] → Только переменная окружения `TELEGRAM_BOT_TOKEN`; при утечке выпустить новый токен
  в BotFather.
- [На демо нет интернета или второго аккаунта Telegram] → Заранее подготовить два аккаунта для сквозного
  сценария и записать запасное видео; вымышленные пользователи остаются только частью наполнения БД.

## Migration Plan

Проект новый, существующих данных нет.

Первичная настройка сервера делается один раз вручную: установить Docker, создать пользователя для деплоя с SSH-ключом,
положить на сервер `infra/docker-compose.prod.yml`, `infra/Caddyfile` и `.env` с секретами, настроить HTTPS-адрес
Mini App и кнопку открытия у бота в BotFather. Дальше каждый коммит в `main` выкатывается пайплайном из решения 13.

Откат — запуск деплоя с образом предыдущего SHA. Миграции Flyway только накатываются вперёд, поэтому миграция, которую
нельзя откатить вместе с образом, исправляется новой миграцией.

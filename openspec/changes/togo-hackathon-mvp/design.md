# Design

## Context

В репозитории уже есть каркас (см. proposal.md, раздел Impact):

- `backend`: Spring Boot 4.1, Kotlin 2.2, Java 21, Maven. Подключены стартеры Web MVC, Data JPA, Flyway, Security,
  Validation и Actuator. Рабочая база — PostgreSQL, но в зависимостях есть и H2.
- `api/openapi.yaml`: контракт API. `openapi-generator` (`kotlin-spring`, `serviceInterface=true`) генерирует
  контроллеры и по одному интерфейсу сервиса на тег в пакет `itmo.goto.generated`. Классы, написанные вручную, например
  `EventsService`, реализуют эти интерфейсы.
- `frontend`: пока только README.
- `infra/docker-compose.yml`: контейнер PostgreSQL 18.

Ограничения: одна неделя, пять разработчиков (двое на бэкенде, двое на фронтенде, один на интеграции, карте и демо),
живое демо в конце.

## Goals / Non-Goals

**Goals:**

- Дать бэкенду и фронтенду работать параллельно со второго дня, зафиксировав контракт в первый день.
- Держать правила событий (лимиты, статус, присоединение и выход) в чистом Kotlin, который тестируется без Spring и базы
  данных.
- Держать демо на публичном сервере с первых дней и обновлять его автоматически из ветки `main`.

**Non-Goals:**

- Горизонтальное масштабирование, кэширование, фоновые задачи.
- Доступность и локализация сверх русского текста интерфейса.
- Инструменты администратора: справочник интересов меняется через миграции.

## Decisions

### 1. Сначала контракт, интерфейсы сервера генерируются

Каждый эндпоинт сначала описывается в `api/openapi.yaml`, потом пишется код. Бэкенд реализует сгенерированные интерфейсы
`*ApiService`. Фронтенд генерирует типы TypeScript из того же файла и работает на заглушках, пока бэкенд не готов.

Планируемый набор эндпоинтов (теги в квадратных скобках):

| Метод и путь                                                                                                                  | Назначение                                    |
|-------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------|
| `POST /api/v1/auth/telegram`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`                                               | [Auth] user-auth                              |
| `GET /api/v1/auth/demo-users`, `POST /api/v1/auth/demo-login` (только в профиле `demo`)                                       | [Auth] демо-вход                              |
| `GET /api/v1/interests`                                                                                                       | [Profile] справочник                          |
| `GET /api/v1/profile`, `PUT /api/v1/profile`, `GET /api/v1/users/{id}`                                                        | [Profile] свой и чужой профиль                |
| `GET /api/v1/events?interest=&city=&from=&to=&hasFreePlaces=`                                                                 | [Events] лента и фильтры                      |
| `POST /api/v1/events`, `GET /api/v1/events/{id}`, `POST /api/v1/events/{id}/cancel`                                           | [Events] создание, карточка, отмена           |
| `POST /api/v1/events/{id}/participants`, `DELETE /api/v1/events/{id}/participants/me`, `GET /api/v1/events/{id}/participants` | [Participation] присоединиться, выйти, список |
| `GET /api/v1/me/events`                                                                                                       | [Participation] мои события                   |
| `GET /api/v1/events/{id}/comments`, `POST /api/v1/events/{id}/comments`                                                       | [Comments]                                    |

Ошибки возвращаются в формате problem details по RFC 9457 (`ProblemDetail` из Spring): 400 при ошибке валидации с
именами полей, 401 без входа, 403 при запрете доступа, 404 если не найдено, 409 при нарушении правил с понятным текстом
в `detail`.

Альтернатива: контроллеры вручную. Отвергнута: генератор уже настроен, а общий контракт — это именно то, что
разблокирует фронтенд.

### 2. Вход через Telegram и сессионная cookie

Spring Security с серверной сессией (`JSESSIONID`, `HttpOnly`, `SameSite=Lax`). Защита от CSRF остаётся включённой в
режиме для SPA (`csrf { spa() }`): токен приходит в cookie `XSRF-TOKEN`, а клиент возвращает его в заголовке
`X-XSRF-TOKEN`.

Фронтенд показывает виджет Telegram Login (скрипт `telegram-widget.js` с `telegram.org`, режим обратного вызова
`data-onauth`). После подтверждения в Telegram виджет отдаёт поля `id`, `first_name`, `last_name`, `username`,
`photo_url`, `auth_date` и `hash`, и фронтенд отправляет их как JSON в `POST /api/v1/auth/telegram`. Бэкенд проверяет
подпись так, как описано в документации Telegram:

- строка для проверки собирается из всех полей, кроме `hash`, в виде `key=value`, отсортированных по ключу и разделённых
  переводом строки;
- секретный ключ равен `SHA-256` от токена бота;
- `HMAC-SHA-256` строки на этом ключе в шестнадцатеричном виде сравнивается с `hash` за постоянное время;
- `auth_date` не старше одного часа по внедрённому `Clock`.

Проверка подписи — чистый компонент без Spring, его тесты подписывают данные тестовым токеном прямо во время теста. После
проверки сервис находит пользователя по `telegram_id` или создаёт нового и открывает сессию. Токен бота берётся из
переменной окружения `TELEGRAM_BOT_TOKEN` и в репозиторий не попадает.

Демо-вход живёт в отдельном компоненте с `@Profile("demo")`: без этого профиля бинов нет, и оба эндпоинта отвечают 404.
Фронтенд показывает выбор демо-пользователя, только если `GET /api/v1/auth/demo-users` ответил 200.

Альтернативы:

- JWT вместо сессии. Отвергнута: нужны хранение токена, его обновление и обработка выхода на клиенте, а демо от этого
  ничего не выигрывает.
- Telegram Mini App (вход по `initData`). Отвергнута: приложение тогда живёт внутри Telegram, а это другая форма
  клиента.
- Вход через диплинк бота (`t.me/<bot>?start=<token>`, бот подтверждает вход). Работает без публичного домена, но
  требует, чтобы бэкенд опрашивал Bot API. Это запасной вариант, если с доменом для виджета не получится.

### 3. Один origin везде

В разработке Vite проксирует `/api` на `localhost:8080`. На сервере сборка SPA лежит в статических ресурсах бэкенда и
отдаётся самим Spring Boot. Получается один процесс, один адрес и никакой настройки CORS.

Виджет Telegram работает только на домене, который привязан к боту командой `/setdomain` в BotFather, и не работает на
`localhost`. Поэтому разработчики локально запускают бэкенд в профиле `demo` и входят через демо-вход. К боту
привязывается домен облачного сервера (решение 12), и вход через настоящий Telegram проверяется там. Пока сервера нет,
его заменяет HTTPS-туннель (cloudflared или ngrok).

### 4. Чистые доменные правила, JPA на краю

Пакет `itmo.goto.domain` содержит Kotlin-код без фреймворков: лимиты участников, вычисление статуса (в точном порядке из
спецификации `event-participation`) и правила присоединения, выхода и отмены. Эти правила превращают запрос либо в новое
состояние, либо в типизированный отказ. Сервисы в `itmo.goto.service` загружают JPA-сущности, вызывают домен и сохраняют
результат. Текущее время приходит из внедрённого `java.time.Clock`, поэтому тесты статуса фиксируют часы, а не ждут.

Альтернатива: правила внутри JPA-сущностей. Отвергнута: таблица статусов — самая рискованная логика недели, и ей нужны
быстрые юнит-тесты без поднятия контекста.

### 5. Статус вычисляется, а не хранится

В базе хранится только отметка времени `cancelled_at`. Статус вычисляется при чтении события. Фильтр «есть свободные
места» превращается в простое SQL-условие `participant_count < max_participants`.

Альтернатива: хранимый статус, который планировщик обновляет в момент начала. Отвергнута: пропущенный запуск оставит
неверный статус, а планировщик добавляет движущуюся часть без видимой пользы.

### 6. Лимит при одновременных запросах: счётчик и блокировка строки

`events.participant_count` — денормализованный счётчик. Присоединение и выход выполняются в одной транзакции. Сначала
она блокирует строку события (`SELECT ... FOR UPDATE` через метод репозитория с `@Lock(PESSIMISTIC_WRITE)`), затем
проверяет доменные правила по заблокированному значению счётчика, затем добавляет или удаляет участие и обновляет
счётчик. Правило «уже участник» дополнительно подкреплено уникальным ограничением на `(event_id, user_id)`.

Альтернатива: оптимистическая блокировка через `@Version`. Отвергнута: проигравший запрос получает общую ошибку
«повторите попытку» вместо понятного ответа «мест нет», которого требует спецификация.

### 7. Модель данных

```
users(id, telegram_id bigint unique, telegram_username null, photo_url null,
      name, city null, created_at)
interests(id, name)                         -- заполняется миграцией
user_interests(user_id, interest_id)        -- первичный ключ по обоим полям
events(id, title, description null, interest_id, city, address,
       latitude null, longitude null, starts_at timestamptz,
       min_participants, max_participants, participant_count,
       organizer_id, cancelled_at null, created_at)
participations(event_id, user_id, joined_at)  -- unique (event_id, user_id)
comments(id, event_id, author_id, text, created_at)
```

Ограничения CHECK повторяют спецификацию: `1 <= min <= max <= 50`, `participant_count <= max_participants`, обе
координаты либо пустые, либо заданы. Индексы: `events(starts_at)`, `events(lower(city))`, `events(interest_id)`.

### 8. Запрос ленты

Один запрос репозитория, который собирается через JPA `Specification` из необязательных фильтров. К нему всегда
добавляются условия `starts_at > now` и `cancelled_at is null` и сортировка по `starts_at`. Пагинации нет: в демо меньше
сотни событий.

### 9. Стек фронтенда

React с TypeScript на Vite, типы из `openapi-typescript`, обработчики MSW по контракту на первые дни. Карта — Leaflet с
тайлами OpenStreetMap через `react-leaflet`: ключ API не нужен, а точка в форме создания выбирается кликом, без
геокодирования адреса.

Альтернатива: Яндекс Карты. Рабочий вариант, но нужен ключ и SDK тяжелее. Переходить на него стоит, только если команда
уже с ним знакома.

### 10. Тесты

Доменные правила — обычные тесты JUnit 5. Репозитории и правило об одновременных запросах — `@DataJpaTest` на PostgreSQL
в Testcontainers с переиспользованием контейнера между тестами, потому что блокировка строки и `lower(city)` на H2 ведут
себя иначе. Веб-слой — срезы `@WebMvcTest` для кодов ответа и problem details. Сценарий гонки запускает два
присоединения в параллельных потоках с ограничением по времени.

### 11. Демо-данные

Отдельная локация Flyway `db/demo`, включённая только в профиле `demo`, добавляет около сорока событий в нескольких
городах, с разными интересами и датами, а также несколько демо-пользователей с выдуманными идентификаторами Telegram.
В тестах и при обычном запуске она не выполняется.

### 12. Сервер: один VPS с Docker Compose

Арендуется один облачный сервер (2 vCPU, 4 ГБ памяти, Ubuntu 24.04) у провайдера, который принимает оплату команды, и
покупается домен с A-записью на IP сервера. На сервере Docker Compose по файлу `infra/docker-compose.prod.yml` запускает
три контейнера:

- `caddy` — принимает HTTPS на портах 80 и 443, сам выпускает и продлевает сертификат Let's Encrypt для домена и
  проксирует запросы в приложение (`infra/Caddyfile`);
- `app` — образ приложения с профилем `demo`; Flyway накатывает миграции при старте;
- `postgres` — PostgreSQL 18 с данными в именованном томе; наружу порт не открыт.

Секреты (`TELEGRAM_BOT_TOKEN`, `POSTGRES_PASSWORD`) лежат только в файле `.env` на сервере, рядом с compose-файлом. В
репозитории их нет, и локальный `infra/docker-compose.yml` тоже берёт пароль из переменной окружения.

Альтернативы:

- Управляемый Kubernetes. Отвергнут: за неделю его настройка не окупится, а нагрузка демо умещается в один сервер.
- Управляемая база данных. Отвергнута: лишние расходы и сетевые настройки, резервные копии демо-данных не нужны.
- PaaS вроде Render или Fly.io. Отвергнут: оплата из России ненадёжна, а вход через Telegram всё равно требует своего
  домена.

### 13. CI/CD на GitHub Actions

Многоэтапный `Dockerfile` в корне репозитория: этап Node собирает SPA, этап Maven собирает jar со сборкой SPA внутри, а
итоговый образ содержит только JRE 21 и jar.

- `.github/workflows/ci.yml` запускается на каждый запрос на слияние и на push в `main`: `./mvnw verify` для бэкенда
  (Testcontainers использует Docker раннера `ubuntu-latest`, зависимости Maven кэшируются) и `npm ci && npm run build`
  для фронтенда.
- `.github/workflows/deploy.yml` запускается после успешного CI на `main`: собирает образ, публикует его в GitHub
  Container Registry с тегом по SHA коммита, затем по SSH выполняет на сервере `docker compose pull` и
  `docker compose up -d` с этим тегом.
- Секреты GitHub: SSH-ключ деплоя, адрес и пользователь сервера. Токен бота и пароль базы в GitHub не хранятся.
- Ветка `main` защищена: слияние только через запрос на слияние с зелёным CI.
- Откат — ручной запуск `deploy.yml` (`workflow_dispatch`) с SHA предыдущего коммита.

Альтернатива: собирать образ прямо на сервере через `git pull`. Отвергнута: сборка Maven и Node нагружает маленький
сервер, а образ из реестра одинаков у CI и сервера.

## Risks / Trade-offs

- [Spring Boot 4 и опция генератора
  `useSpringBoot4` появились недавно, и сгенерированный код может не скомпилироваться для некоторых схем] → Описать
  эндпоинты в контракте в первый день и сразу собрать проект, чтобы проблемы генератора всплыли до того, как от них
  кто-то зависит.
- [CSRF в режиме SPA — самый частый источник загадочных ошибок 403] → Подключить его во второй день вместе с первым
  защищённым эндпоинтом и сквозной проверкой, а не на пятый.
- [Тайлам OpenStreetMap во время демо нужен интернет] → Записать запасное видео главного сценария в седьмой день.
- [Путаница с часовыми поясами в фильтрах и статусе] → `timestamptz` в базе, `OffsetDateTime` в API, браузер передаёт
  смещение, тесты фиксируют часы.
- [Денормализованный счётчик может разойтись со строками участия] → Его меняют только два метода сервиса под
  блокировкой, а ограничение CHECK не даёт ему превысить максимум.
- [Нет публичного домена, и виджет Telegram не работает] → Создать бота во второй день и привязать к нему домен сервера,
  а до появления сервера — туннель; если с доменом не получается, перейти на вход через диплинк бота из решения 2.
- [Оплата сервера, DNS и выпуск сертификата займут дни] → Купить сервер и домен в первый день, а во второй задеплоить
  пустой каркас через пайплайн, пока на нём ничего не зависит.
- [Демо-вход на публичном сервере доступен любому] → Для хакатона это допустимо, демо-данные не личные; после демо
  выключить профиль `demo` или сервер.
- [Пароль базы открытым текстом в `infra/docker-compose.yml` и `application.properties`] → Перенести его в переменные
  окружения вместе с первой задачей по серверу.
- [Тесты на Testcontainers замедляют CI] → Кэшировать зависимости Maven и переиспользовать контейнер внутри одного
  запуска.
- [Токен бота утечёт в репозиторий] → Только переменная окружения `TELEGRAM_BOT_TOKEN`; при утечке выпустить новый токен
  в BotFather.
- [На демо нет интернета или нескольких аккаунтов Telegram] → Второго и следующих участников показывать через демо-вход,
  запасное видео записать заранее.
- [H2 в зависимостях соблазняет тестировать на нём] → Использовать только Testcontainers и удалить H2 вместе с первым
  тестом репозитория.

## Migration Plan

Проект новый, существующих данных нет.

Первичная настройка сервера делается один раз вручную: установить Docker, создать пользователя для деплоя с SSH-ключом,
положить на сервер `infra/docker-compose.prod.yml`, `infra/Caddyfile` и `.env` с секретами, привязать домен сервера к
боту в BotFather. Дальше каждый коммит в `main` выкатывается пайплайном из решения 13.

Откат — запуск деплоя с образом предыдущего SHA. Миграции Flyway только накатываются вперёд, поэтому миграция, которую
нельзя откатить вместе с образом, исправляется новой миграцией.

## Open Questions

- Какой облачный провайдер и какой домен. Подход из решения 12 подходит любому провайдеру с VPS на Ubuntu, поэтому выбор
  меняет только первичную настройку сервера.
- Точный список интересов в справочнике. Это данные миграции, их можно поменять в любой момент.

# Design

## Context

В репозитории уже есть каркас (см. proposal.md, раздел Impact):

- `backend`: Spring Boot 4.1, Kotlin 2.2, Java 21, Maven. Подключены стартеры Web MVC, Data JPA, Flyway, Security,
  Validation и Actuator. Рабочая база — PostgreSQL, но в зависимостях есть и H2.
- `api/openapi.yaml`: контракт API. `openapi-generator` (`kotlin-spring`, `serviceInterface=true`) генерирует
  контроллеры и по одному интерфейсу сервиса на тег в пакет `itmo.goto.generated`. Классы, написанные вручную, например
  `EventsService`, реализуют эти интерфейсы.
- `frontend`: каркас Vue 3 на Vite со страницами ленты, создания события, профиля и карты.
- `infra/docker-compose.yml`: контейнер PostgreSQL 18.

Требования уточнены по аналитике команды:
https://docs.google.com/document/d/19rsIFeIvy4lMbOKaGxInJH8MMWmOxSxdXBwLJBqDgPc. Аналитика перечисляет четыре статуса
события; «Набор пользователей» соответствует `recruiting`, «Все в сборе» — `registration_closed`, а `finished`
остаётся из контракта. Таблица ERD в аналитике упрощена: там, где она расходится с решением 7, верно решение 7.

## Goals / Non-Goals

**Goals:**

- Дать бэкенду и фронтенду работать параллельно со второго дня, зафиксировав контракт в первый день.
- Держать правила событий (лимиты, статус, присоединение и выход) в чистом Kotlin, который тестируется без Spring и базы
  данных.
- Держать демо на публичном сервере с первых дней и обновлять его автоматически из ветки `main`.

**Non-Goals:**

- Горизонтальное масштабирование и кэширование. Из фоновой обработки нужен только переход состояний событий по срокам.
- Доступность и локализация сверх русского текста интерфейса.
- Инструменты администратора: перечень категорий меняется только вместе с контрактом и кодом.
- Раздел «Друзья», социальный граф и приглашения друзей: в навигации и экранах MVP их нет.
- Роль гостя: приложение работает только для вошедшего через Telegram пользователя.

## Decisions

### 1. Контракт — источник истины, интерфейсы сервера генерируются

`api/openapi.yaml` — источник истины для API. Если спецификации или этот документ расходятся с контрактом, верен
контракт, а артефакты исправляются. Каждый новый эндпоинт сначала описывается в контракте, потом пишется код. Бэкенд
реализует сгенерированные интерфейсы `*ApiService`. Фронтенд генерирует типы TypeScript из того же файла и работает
на заглушках, пока бэкенд не готов. Существующие поля и эндпоинты не меняются; недостающее добавляется новыми
необязательными полями, параметрами и эндпоинтами.

Эндпоинты контракта (теги в квадратных скобках, «+» — добавление этого изменения):

| Метод и путь                                                                     | Назначение                                     |
|----------------------------------------------------------------------------------|------------------------------------------------|
| `POST /api/v1/auth/telegram`                                                     | [Auth] вход по initData                        |
| `GET /api/v1/users/me`, + `PUT /api/v1/users/me`                                 | [Users] свой профиль                           |
| + `GET /api/v1/users/{userId}`                                                   | [Users] чужой профиль                          |
| `GET /api/v1/categories`                                                         | [Categories] перечень категорий                |
| `GET /api/v1/events?query=&category=&startsFrom=&startsTo=&state=&participating=&limit=&offset=`, + `hasFreePlaces=`, + `order=` | [Events] лента, фильтры, «мои события», архив |
| `POST /api/v1/events`, `GET /api/v1/events/{eventId}`, `PATCH /api/v1/events/{eventId}` | [Events] создание, карточка, изменение  |
| `POST /api/v1/events/{eventId}/cancel`                                           | [Events] отмена организатором                  |
| `GET /api/v1/events/{eventId}/participants`                                      | [Events] список участников                     |
| `PUT` и `DELETE /api/v1/events/{eventId}/participants/me`                        | [Events] присоединиться и выйти                |
| + `GET` и `POST /api/v1/events/{eventId}/comments`                               | [Comments] комментарии                         |

Добавления схем:

- `CurrentUser` получает `name`, `photoUrl` (nullable), `city` (nullable) и `categories`; новые `UserProfile`
  (без `tgId`) и `UpdateProfileRequest` с `name`, `city` и `categories`.
- `Event` и `CreateEventRequest` получают nullable `latitude` и `longitude`; в `PATCH` их нет, как и `location`.
- `CreateEventRequest` и `UpdateEventRequest`: `maxLength: 100` у `title`, `maxLength: 2000` у `description`,
  `maximum: 50` у `minUsers` и `maxUsers`.
- Новые `Comment`, `CreateCommentRequest` (`text` до 1000 символов) и `CommentPage` с `limit` и `offset`.
- `ApiError.code` получает `USER_NOT_FOUND`; `FORBIDDEN` также означает запрет комментировать не участнику.
- `CurrentUser` и `UserProfile` получают `createdEventsCount` и `visitedEventsCount`; `ApiError.code` получает
  `SCHEDULE_CONFLICT` и `ACTIVE_EVENT_LIMIT`.
- `GET /api/v1/events` получает необязательный `order` (`asc` \| `desc`, по умолчанию `asc`).

Единственное исключение из правила добавлений согласовано по аналитике и ревью и вносится до появления клиентов,
которые от него зависят:

- `description` в `CreateEventRequest` становится обязательным, в `CreateEventRequest` и `UpdateEventRequest`
  получает `maxLength: 500` и `minLength: 1`.
- Категория становится перечнем `EventCategory` со значениями `PICNIC` («Пикник»), `RUN` («Пробежка»), `EXCURSION`
  («Поход на экскурсию»), `BOARD_GAMES` («Настолки»), `QUEST` («Квест»), `CINEMA` («Кино») и `CAFE`
  («Кафе/Ресторан»). У события одно поле `category`: обязательное в `CreateEventRequest`, необязательное
  в `UpdateEventRequest`, всегда заполненное в `Event`; оно заменяет `categoryIds` и массив категорий события.
  Фильтр ленты `category` заменяет `categoryId`. В профиле `categories` и в `UpdateProfileRequest` — набор значений
  перечня без повторов. `GET /api/v1/categories` отдаёт пары `code` и `name` в порядке объявления перечня.
- Неизвестное значение категории отклоняется как 400 VALIDATION_ERROR; код `CATEGORY_NOT_FOUND` удаляется
  из `ApiError.code`.

Ошибки возвращаются в формате `ApiError { code, message, details }` из контракта, а не problem details:
400 VALIDATION_ERROR с полями в `details`, 401 UNAUTHORIZED с `WWW-Authenticate: Bearer`,
403 FORBIDDEN, 404 EVENT_NOT_FOUND или USER_NOT_FOUND, 409 с кодом нарушенного правила, включая SCHEDULE_CONFLICT и
ACTIVE_EVENT_LIMIT, 500 INTERNAL_ERROR без внутренних деталей. Неизвестные поля запроса отклоняются с 400
VALIDATION_ERROR.

Альтернатива: контроллеры вручную. Отвергнута: генератор уже настроен, а общий контракт — это именно то, что
разблокирует фронтенд.

### 2. Автоматический вход Telegram Mini App

При запуске внутри Telegram фронтенд получает исходную строку `Telegram.WebApp.initData` и отправляет
`{ "initData": "..." }` в `POST /api/v1/auth/telegram`. Формы входа, Telegram Login Widget и выбора
демо-пользователя нет. После успеха клиент открывает приложение под пользователем Telegram.

Бэкенд проверяет данные по алгоритму Mini App:

- Разделяет query string на пары и URL-декодирует ключи и значения ровно один раз; дубли ключей отклоняются.
- Удаляет `hash`, сортирует остальные поля и собирает `key=value` с разделителем `\n`. Значение `user` до проверки
  подписи сохраняется в исходном декодированном виде, без повторной JSON-сериализации.
- Вычисляет `secretKey = HMAC_SHA256(key="WebAppData", data=botToken)`, затем
  `expectedHash = HMAC_SHA256(key=secretKey, data=dataCheckString)`; сравнивает байты подписи за постоянное время.
- Проверяет через внедрённый `Clock`, что `auth_date` не старше 5 минут и не опережает сервер более чем на 30 секунд.
- Требует подписанный `user` с корректным Telegram ID. `initDataUnsafe`, отдельно присланный ID и username
  не являются основанием для аутентификации. Любой отказ не создаёт пользователя и не выдаёт токен.

Алгоритм: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app.
Проверка — чистый компонент без Spring; тесты используют вымышленный токен бота и фиксированное время.
Токен бота берётся из `TELEGRAM_BOT_TOKEN`, не передаётся клиенту и не логируется вместе с `initData`.
После проверки сервис находит или создаёт пользователя по Telegram ID, обновляет username из проверенных данных
и не затирает самостоятельно изменённое имя профиля.

Текущий контракт возвращает `accessToken`, `tokenType: Bearer`, `expiresIn: 3600` и `user`.
Все последующие запросы, кроме входа, требуют `Authorization: Bearer <accessToken>`.
Токен — JWT с подписью HS256, `sub` содержит UUID пользователя, срок проверяется по внедрённому `Clock` без допуска.
Ключ подписи выводится из токена бота как `HMAC_SHA256(key="ToGo access token", data=botToken)`, поэтому отдельный
секрет не нужен: владелец токена бота и так может подделать `initData`.
Spring Security проверяет подлинность и срок действия токена приложения; аутентификация через cookie,
`formLogin` и HTTP Basic не используется. CSRF для этого API отключается только при условии, что сервер
не принимает автоматически отправляемые браузером cookie как средство аутентификации.

Токен хранится клиентом в памяти. После перезагрузки клиент повторяет обмен ещё свежего `initData`;
после 401 или при просроченном `initData` очищает токен и показывает предложение переоткрыть Mini App.
Без `initData` обычная сборка показывает сообщение об открытии через Telegram, не форму логина.
Отдельная публичная демо-сборка разрешает явный вход в тестовый профиль через MSW только без `initData`;
при запуске из Telegram она отключает моки и использует настоящий серверный вход.
Серверного logout и refresh в текущем контракте нет. Обсуждённая refresh-сессия — отдельное будущее изменение
контракта и хранения; этот план не обещает автоматическое продление access token.

Альтернатива: Telegram Login Widget и сессионная cookie. Не выбрана, потому что продукт запускается как Mini App
внутри Telegram и использует предоставленные Telegram подписанные данные запуска.

### 3. Один origin и запуск внутри Telegram

В разработке Vite проксирует `/api` на `localhost:8080`. На сервере nginx отдаёт SPA из frontend-контейнера,
а `/api/` направляет в Spring Boot; API и клиент используют один origin.

В BotFather настраивается HTTPS-адрес Mini App и кнопка её открытия. Настоящий вход проверяется запуском
Mini App внутри Telegram по этому адресу. До появления сервера используется HTTPS-туннель.
При обычном открытии URL в браузере без данных запуска сервер не выдаёт токен.
Для разработки интерфейса MSW подменяет ответы API локально. Отдельная публичная демо-сборка
использует MSW только вне Telegram и обозначает тестовый профиль на экране входа. Она не меняет
серверную проверку `initData`; профиль `demo` отвечает только за тестовый набор данных.

Бот получает обновления по `POST /api/v1/bot/webhook`. Telegram устанавливает webhook с отдельным
`secret_token`; сервер сравнивает его с заголовком `X-Telegram-Bot-Api-Secret-Token` и отклоняет
несовпадение. На `/start` в личном чате бот отправляет русское приветствие и кнопку `web_app` на
`https://dev-togo.ru/`. Другие обновления подтверждает без действия. Bot API вызывается из
существующего Spring Boot через HTTP-клиент; `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET`
хранятся только на сервере. Регистрация webhook выполняется после развёртывания обработчика.

### 4. Чистые доменные правила, JPA на краю

Пакет `itmo.goto.domain` содержит Kotlin-код без фреймворков: лимиты участников, переходы состояний по сроку регистрации и окончания
из спецификации `event-participation`, правила присоединения, выхода и отмены, правило пересечения по времени и лимит
пяти активных событий пользователя. Эти правила превращают запрос либо в новое состояние, либо в типизированный отказ.
Сервисы в `itmo.goto.service` загружают JPA-сущности, вызывают домен и сохраняют результат. Текущее время приходит из
внедрённого `java.time.Clock`, поэтому тесты статуса фиксируют часы, а не ждут.

Альтернатива: правила внутри JPA-сущностей. Отвергнута: таблица статусов — самая рискованная логика недели, и ей нужны
быстрые юнит-тесты без поднятия контекста.

### 5. Срок регистрации и состояния события

`registrationClosesAt` из `api/openapi.yaml` — источник истины для возможности изменить состав участников.
Организатор задаёт его при создании: `now < registrationClosesAt <= startsAt < endsAt`.
`startsAt` определяет начало встречи и последнюю возможность отмены организатором, но не заменяет срок регистрации.
Все даты передаются с часовым поясом и хранятся в `timestamptz`.

В БД хранится `state` с пятью значениями API:

- `recruiting`: набор открыт, пока `now < registrationClosesAt`;
- `registration_closed`: срок регистрации наступил и минимум набран; состав зафиксирован, встреча ожидается или идёт;
- `cancelled_by_system`: к сроку регистрации минимум не набран;
- `cancelled_by_organizer`: организатор отменил встречу до `startsAt`;
- `finished`: у неотменённой встречи наступил `endsAt`.

При достижении минимума или заполнении мест состояние остаётся `recruiting`. Число свободных мест отображается
отдельно; положительное число не даёт права вступить после срока регистрации. При `now == registrationClosesAt`
вступление и выход уже запрещены. Отменённые события не переходят в `finished` и сохраняют участников.

Фоновая обработка закрывает набор и завершает встречи. Повторное вступление участника, выход не участника и повторная отмена отменённого организатором события
идемпотентны: сервер отвечает успехом без изменений, как требует контракт. Каждая операция над событием под блокировкой сначала
актуализирует его состояние по серверному времени, затем проверяет допустимость действия. При задержке обработки
событие не остаётся открытым: чтение карточки и списка также возвращает актуальное состояние, а фильтры применяются
к нему до выборки результатов. Если обработка впервые произошла после `endsAt`, сначала проверяется минимум
при закрытии регистрации, затем успешное событие переводится в `finished`; недобор остаётся `cancelled_by_system`.

Альтернатива: вычислять шесть прежних статусов только по `startsAt` и числу участников. Не выбрана, потому что
она допускает изменение состава после заданного организатором срока и не соответствует состояниям API.

### 6. Лимит при одновременных запросах: счётчик и блокировка строки

`events.participants_count` — денормализованный счётчик. Присоединение и выход выполняются в одной транзакции. Сначала
она блокирует строку события (`SELECT ... FOR UPDATE` через метод репозитория с `@Lock(PESSIMISTIC_WRITE)`), затем
считывает серверное время после получения блокировки, актуализирует состояние и проверяет
`now < registrationClosesAt` и доменные правила по заблокированному счётчику. Только затем добавляет или удаляет
участие и обновляет счётчик. Закрытие регистрации, перенос её срока и отмена используют ту же блокировку.
Если запрос ждал блокировку и получил её после дедлайна, он не меняет состав, даже если поступил раньше.
Актуализация состояния должна сохраняться и при отказе в действии: типизированный отказ возвращается из
транзакции и преобразуется в HTTP-ошибку после commit, чтобы не откатить закрытие регистрации. Правило «уже участник» дополнительно подкреплено уникальным ограничением на `(event_id, user_id)`.

Правило пересечения по времени отклоняет вступление и создание события с 409 SCHEDULE_CONFLICT, если пользователь
участвует в другом событии в `recruiting` или `registration_closed`, начало которого отстоит от начала нового меньше
чем на три часа; ровно три часа допустимы. Проверяется после состояния, срока регистрации и вместимости, по
актуальному состоянию других событий из решения 5. Чтобы два параллельных вступления одного пользователя в разные
события не обошли правило, вступление после блокировки события блокирует строку пользователя, а создание события
блокирует только строку пользователя. Порядок «событие, затем пользователь» один для всех операций, поэтому
взаимной блокировки нет.

Лимит пяти активных событий: активным считается участие в событии в `recruiting` или `registration_closed`
(включая организованные). Создание события и вступление отклоняются с 409 ACTIVE_EVENT_LIMIT, если у пользователя
уже есть пять таких участий. Проверка идёт после блокировки строки пользователя, вместе с правилом пересечения,
чтобы параллельные запросы не обошли потолок. Отменённые и завершённые события лимит не занимают. Пока кода нет
в контракте, фронтенд не обрабатывает этот отказ; после появления кода — показывает сообщение из `ApiError`.

Альтернатива: оптимистическая блокировка через `@Version`. Отвергнута: проигравший запрос получает общую ошибку
«повторите попытку» вместо понятного ответа «мест нет», которого требует спецификация.

### 7. Модель данных

Миграция `V1__base_structure.sql` уже есть и могла быть применена локально, поэтому её не правят: изменения вносит
новая миграция `V2`. Уточнения по аналитике и ревью вносит миграция `V3`: она удаляет таблицы `categories`
и `event_categories`, добавляет `events.category`, пересоздаёт `user_categories` со значением перечня вместо ссылки,
делает `events.description` обязательным от 1 до 500 символов и создаёт `notifications`. Значения категорий
хранятся строками кодов перечня и ограничены CHECK. Локальные базы с тестовыми событиями пересоздаются.

```
users(id uuid, tg_id bigint unique, tg_login null,
      + name, + photo_url null, + city null, + created_at)
+ user_categories(user_id, category)                  -- первичный ключ по обоим полям, category из перечня
events(id uuid, title, description, location, icon null,
       starts_at timestamptz, ends_at timestamptz, registration_closes_at timestamptz,
       state, min_users, max_users, organizer_id, + category,
       + participants_count, + latitude null, + longitude null, + created_at)
event_users(id, event_id, user_id, + joined_at)       -- unique (event_id, user_id)
+ comments(id uuid, event_id, author_id, text, created_at)
+ notifications(id uuid, user_id, event_id, kind, due_at, sent_at null, attempts)  -- unique (user_id, event_id, kind)
```

Счётчики профиля не хранятся, в отличие от `created_events` и `visited_events` в ERD аналитики: их считают запросы
к `events.organizer_id` и к `event_users` с событиями в `finished`, чтобы счётчики не расходились с данными.

Ограничения CHECK повторяют контракт: `1 <= min_users <= max_users <= 50`,
`1 <= participants_count <= max_users`, обе координаты либо пустые, либо заданы и лежат в допустимых диапазонах,
`registration_closes_at <= starts_at < ends_at`, `state` ограничен пятью значениями из решения 5, длина
`title` до 100, `description` от 1 до 500, `comments.text` от 1 до 1000 символов. Проверка `registrationClosesAt > now`
выполняется сервисом при создании и изменении срока, а не динамическим CHECK. Индексы: `events(starts_at)`,
`events(organizer_id)`, `event_users(user_id)`, `events(category)`,
`events(registration_closes_at) WHERE state = 'recruiting'`, `events(ends_at) WHERE state = 'registration_closed'`,
`comments(event_id, created_at)`, `notifications(due_at) WHERE sent_at IS NULL`.

### 8. Запрос ленты

Один запрос репозитория, который собирается через JPA `Specification` из необязательных фильтров контракта:
`query` (`lower(title) LIKE`), `category` (равенство `events.category`), `startsFrom` включительно, `startsTo`
исключительно, `state`, `participating` (через `event_users` текущего пользователя) и `hasFreePlaces`
(`state = 'recruiting'`, `registration_closes_at > now`, `participants_count < max_users`). Фильтр по состоянию
применяется к актуальному состоянию: перед выборкой сервис актуализирует события с наступившими сроками по
решению 5. Пагинация `limit` и `offset`, `total` считается отдельным запросом с теми же условиями. Порядок задаёт
необязательный `order`: по умолчанию и при `asc` — `starts_at ASC, id ASC`; при `desc` — `starts_at DESC, id DESC`.
Клиент НЕ разворачивает страницу сам: разворот на клиенте ломает пагинацию истории. По умолчанию состояние не
фильтруется: прошедшие и отменённые события тоже возвращаются, а экран ленты сам передаёт `startsFrom=now` и
`limit=12` (дефолт контракта `limit=20` не меняется). Требование аналитики «бэкенд возвращает только ещё не
наступившие события» выполняется параметром экрана: умолчание сервера не меняется.

«Мои события» — тот же запрос с `participating=true`: клиент делает два запроса, `startsFrom=now` с `order=asc` для
предстоящих и `startsTo=now` с `order=desc` для прошедших. Архив в своём профиле — отдельные запросы с
`participating=true`, фильтрами `state` на `finished`, `cancelled_by_organizer` и `cancelled_by_system`,
`order=desc` и `limit=12`. Чужой профиль архива не показывает. Отдельного эндпоинта нет.

### 9. Стек фронтенда

Уточнение профиля по разделу 6 аналитики: блок интересов и их редактирование убраны из своего и чужого
профиля. `categories` пока остаётся в API; фронтенд сохраняет его без изменений при редактировании имени.
Удаление поля из контракта и БД не входит в эту UI-правку. Город и редактор имени остаются по OpenSpec;
их отсутствие в описании аналитики требует отдельного продуктового решения.

Vue 3 с TypeScript на Vite, архитектура FEOD, TanStack Query для серверного состояния и Pinia для клиентского состояния.
Типы генерируются через `openapi-typescript`, обработчики MSW работают по контракту на первые дни. Карта использует
Leaflet и тайлы OpenStreetMap. По уточнённому решению команды пользователь выбирает только готовое место
маркером или кнопкой списка; ручного ввода адреса и произвольного клика по карте нет. До согласования API мест
компонент `PlacePicker` получает локальный `demoPlaces`. Название и адрес показаны под картой;
координаты выбранного места передаются вместе. Значок Leaflet скрыт, атрибуция OpenStreetMap сохранена.
Для публичных тайлов нужно
соблюдать правила использования и указывать авторство OpenStreetMap; доступность сервиса не гарантируется.

Telegram-авторизация и бот подключены. Отдельная фронтенд-сборка
`--mode demo` сохраняет «Войти в демо» только вне Telegram. Наличие `initData` или платформы Telegram
безусловно отключает моки, в том числе при `VITE_MSW_ENABLED=true`; явный `false` отключает их и снаружи.
Обычная production-сборка остаётся без мокового входа. Это не серверная авторизация и не доступ
к настоящим данным. Webhook и приветствие бота уже есть в `origin/main`; очередь событийных уведомлений
пока в отдельной ветке `origin/bot-notifications`, не считается частью проверенного релиза.

Экран из макета «Войти / Telegram / Зарегистрироваться» не применяется к Mini App. `AuthGate` показывает
компактный логотип и автоматическую загрузку, при сетевой ошибке — повтор, при истёкшей сессии — инструкцию
переоткрыть приложение. В обычном браузере без данных запуска — страница со ссылкой на бота;
в явно включённом внешнем демо — пояснение о тестовых данных. `/login` перенаправляет на главную,
отдельной формы и ручного шага входа внутри Telegram нет. Разрешение `requestWriteAccess`
запрашивается после успешной авторизации и не блокирует её при отказе пользователя.
После слияния UI из PR #9 общий API-клиент остаётся in-memory и без повторов на 401;
все новые экраны используют типы из `schema.ts`. Параметр `order` пока только запланирован (1.8/8.4):
до его появления архив читает все страницы и сортирует полный список, не разворачивает первую страницу отдельно.

В форме создания нет дублирующих нативных date/time-полей: только кастомный календарь и кнопка-поле времени.
По последнему уточнению пользователя вместо ползунка из аналитики 4.4 поле времени раскрывает два
кастомных переключателя «Часы / Минуты» со стрелками и числовым вводом (часы с шагом 1, минуты с шагом 5);
введённые минуты округляются вниз до ближайшей пятиминутки. Значение применяется
явным выбором, без скрытого заполнения начала, окончания или срока регистрации. В ленте поиск отделён
от карточек отступом. Основные API событий уже подключены через общий клиент; демо-режим сохранён
только вне Telegram, настоящий бэкенд не принимает моковый токен.

Альтернатива: Яндекс Карты. Рабочий вариант, но нужен ключ и SDK тяжелее. Переходить на него стоит, только если команда
уже с ним знакома.

### 10. Тесты

Доменные правила — обычные тесты JUnit 5. Репозитории и правило об одновременных запросах — `@DataJpaTest` на PostgreSQL
в Testcontainers с переиспользованием контейнера между тестами, потому что блокировка строки и `uuidv7()` на H2 ведут
себя иначе. Веб-слой — срезы `@WebMvcTest` для кодов ответа и формата `ApiError`. Сценарий гонки запускает два
присоединения в параллельных потоках с ограничением по времени.

### 11. Демо-данные

Отдельная локация Flyway `db/demo`, включённая только в профиле `demo`, добавляет около сорока событий в разных местах,
с разными категориями и датами, а также несколько демо-пользователей с выдуманными идентификаторами Telegram.
В тестах и при обычном запуске она не выполняется. Для событий задаются согласованные `registration_closes_at`,
`starts_at`, `ends_at` и `state`. Записи вымышленных пользователей нужны для наполнения событий, но не дают
возможности войти от их имени: сквозной вход показывается на настоящих аккаунтах Telegram.

### 12. Сервер: один VPS с Docker Compose

Арендуется один облачный сервер (2 vCPU, 4 ГБ памяти, Ubuntu 24.04) у провайдера, который принимает оплату команды, и
покупается домен с A-записью на IP сервера. На сервере Docker Compose по файлу `infra/docker-compose.prod.yml` запускает
три контейнера:

- `caddy` — принимает HTTPS на портах 80 и 443, сам выпускает и продлевает сертификат Let's Encrypt для домена и
  проксирует запросы в приложение (`infra/Caddyfile`);
- `app` — образ приложения с профилем `demo`; Flyway накатывает миграции при старте;
- `postgres` — PostgreSQL 18 с данными в именованном томе; наружу порт не открыт.

Секреты (`TELEGRAM_BOT_TOKEN`, `POSTGRES_PASSWORD`) лежат только в файле `.env` на сервере, рядом с compose-файлом. В
репозитории их нет, и локальный `infra/docker-compose.yml` тоже берёт пароль из переменной окружения.

Альтернативы:

- Управляемый Kubernetes. Отвергнут: за неделю его настройка не окупится, а нагрузка демо умещается в один сервер.
- Управляемая база данных. Отвергнута: лишние расходы и сетевые настройки, резервные копии демо-данных не нужны.
- PaaS вроде Render или Fly.io. Отвергнут: оплата из России ненадёжна, а вход через Telegram всё равно требует своего
  домена.

### 13. CI/CD на GitHub Actions

Многоэтапный `Dockerfile` в корне репозитория: этап Node собирает SPA, этап Maven собирает jar со сборкой SPA внутри, а
итоговый образ содержит только JRE 21 и jar.

- `.github/workflows/ci.yml` запускается на каждый запрос на слияние и на push в `main`: `./mvnw verify` для бэкенда
  (Testcontainers использует Docker раннера `ubuntu-latest`, зависимости Maven кэшируются) и `npm ci && npm run build`
  для фронтенда.
- `.github/workflows/deploy.yml` запускается после успешного CI на `main`: собирает образ, публикует его в GitHub
  Container Registry с тегом по SHA коммита, затем по SSH выполняет на сервере `docker compose pull` и
  `docker compose up -d` с этим тегом.
- Секреты GitHub: SSH-ключ деплоя, адрес и пользователь сервера. Токен бота и пароль базы в GitHub не хранятся.
- Ветка `main` защищена: слияние только через запрос на слияние с зелёным CI.
- Откат — ручной запуск `deploy.yml` (`workflow_dispatch`) с SHA предыдущего коммита.

Альтернатива: собирать образ прямо на сервере через `git pull`. Отвергнута: сборка Maven и Node нагружает маленький
сервер, а образ из реестра одинаков у CI и сервера.

### 14. Уведомления через бота: очередь в базе и планировщик

Операция, после которой нужно уведомление, в той же транзакции записывает строку `notifications`: вступление —
`joined` для вступившего, закрытие набора с набранным минимумом — `confirmed` для каждого участника, отмена —
`cancelled` для участников, кроме организатора при его собственной отмене. Создание события и вступление записывают
напоминания `reminder_day` и `reminder_hour` на `startsAt` минус сутки и минус час, если эти моменты ещё впереди;
выход удаляет неотправленные напоминания пользователя. Уникальность `(user_id, event_id, kind)` исключает повторы.

Задача `@Scheduled` раз в минуту выбирает строки с наступившим `due_at`, пропускает напоминания отменённых событий,
отправляет текст на русском через Bot API `sendMessage` с `chat_id`, равным Telegram ID, и отмечает `sent_at`. Ответ
403 (бот заблокирован или не получал разрешения) закрывает строку без повторов, прочие ошибки повторяются до трёх
попыток. Клиент при первом запуске вызывает `Telegram.WebApp.requestWriteAccess`, чтобы бот мог писать пользователю.
Время берётся из внедрённого `Clock`, а адрес Bot API настраивается, чтобы тесты подменяли его локальным сервером.

Альтернатива: отправлять сообщение прямо в запросе пользователя. Отвергнута: задержки и сбои Telegram попали бы
под блокировку события и в результат операции.

## Risks / Trade-offs

- [Spring Boot 4 и опция генератора
  `useSpringBoot4` появились недавно, и сгенерированный код может не скомпилироваться для некоторых схем] → Описать
  эндпоинты в контракте в первый день и сразу собрать проект, чтобы проблемы генератора всплыли до того, как от них
  кто-то зависит.
- [Access token истёк, а старые initData больше не принимаются] → Обработать 401 без бесконечных повторов,
  очистить токен и предложить переоткрыть Mini App; refresh не считать уже реализованным.
- [Фоновое закрытие регистрации задержалось] → Проверять серверное время после блокировки и возвращать
  актуальное состояние при чтении; покрыть тестами ровно дедлайн и запрос, ожидающий блокировку.
- [Тайлам OpenStreetMap во время демо нужен интернет] → Записать запасное видео главного сценария в седьмой день.
- [Путаница с часовыми поясами в фильтрах и статусе] → `timestamptz` в базе, `OffsetDateTime` в API, браузер передаёт
  смещение, тесты фиксируют часы.
- [Денормализованный счётчик может разойтись со строками участия] → Его меняют только два метода сервиса под
  блокировкой, а ограничение CHECK не даёт ему превысить максимум.
- [Нет HTTPS-адреса для запуска Mini App] → Настроить адрес сервера у бота во второй день; до появления сервера
  использовать HTTPS-туннель и проверять запуск именно внутри Telegram.
- [Оплата сервера, DNS и выпуск сертификата займут дни] → Купить сервер и домен в первый день, а во второй задеплоить
  пустой каркас через пайплайн, пока на нём ничего не зависит.
- [Моки разработки попадут в демо] → Не включать MSW в публичную сборку; профиль `demo` меняет только данные
  и не разрешает обход проверки подписи Telegram.
- [Пароль базы открытым текстом в `infra/docker-compose.yml` и `application.properties`] → Перенести его в переменные
  окружения вместе с первой задачей по серверу.
- [Тесты на Testcontainers замедляют CI] → Кэшировать зависимости Maven и переиспользовать контейнер внутри одного
  запуска.
- [Токен бота утечёт в репозиторий] → Только переменная окружения `TELEGRAM_BOT_TOKEN`; при утечке выпустить новый токен
  в BotFather.
- [На демо нет интернета или второго аккаунта Telegram] → Заранее подготовить два аккаунта для сквозного
  сценария и записать запасное видео; вымышленные пользователи остаются только частью наполнения БД.
- [Сужение контракта для описания и категорий нарушает правило добавлений] → Внести его одной задачей до того, как
  фронтенд начнёт отправлять события, и зафиксировать исключение в решении 1.
- [Бот не может написать пользователю, который не дал разрешения] → Запрашивать `requestWriteAccess` при первом запуске,
  не повторять отправку после 403 и не считать уведомления обязательной частью сценария.
- [Сбой между отправкой и отметкой `sent_at` даёт повторное сообщение] → Принять редкий дубль ради простоты очереди.
- [H2 в зависимостях соблазняет тестировать на нём] → Использовать только Testcontainers и удалить H2 вместе с первым
  тестом репозитория.

## Migration Plan

Проект новый, существующих данных нет.

Первичная настройка сервера делается один раз вручную: установить Docker, создать пользователя для деплоя с SSH-ключом,
положить на сервер `infra/docker-compose.prod.yml`, `infra/Caddyfile` и `.env` с секретами, настроить HTTPS-адрес
Mini App и кнопку открытия у бота в BotFather. Дальше каждый коммит в `main` выкатывается пайплайном из решения 13.

Откат — запуск деплоя с образом предыдущего SHA. Миграции Flyway только накатываются вперёд, поэтому миграция, которую
нельзя откатить вместе с образом, исправляется новой миграцией.

## Open Questions

- Какой облачный провайдер и какой домен. Подход из решения 12 подходит любому провайдеру с VPS на Ubuntu, поэтому выбор
  меняет только первичную настройку сервера.
- Значения по умолчанию для `endsAt` и `registrationClosesAt` в форме создания: аналитика описывает только дату и время
  начала, а контракт требует все три момента.
- Вопросы аналитики вне MVP: отзывы на события, для каких городов приложение и хранить ли иконки отдельной таблицей.

Закрыто по QA аналитики: архив завершённых и отменённых встреч текущего пользователя — в MVP (секция своего
профиля); роль гостя не нужна; лимит пяти активных событий (`recruiting` / `registration_closed`) — в MVP с кодом
`ACTIVE_EVENT_LIMIT`; раздел «Друзья» в UI не делается.

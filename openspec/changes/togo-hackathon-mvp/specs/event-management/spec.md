# Spec Delta

## Purpose

Позволяет вошедшему пользователю организовать встречу: создать событие со временем, местом и лимитами участников, а
потом при необходимости отменить его.

## ADDED Requirements

### Requirement: Создание события

Система ДОЛЖНА (SHALL) позволять вошедшему пользователю создать событие с названием, необязательным описанием, одним
интересом из справочника, городом, адресом, временем начала и окончания, сроком регистрации `registrationClosesAt`,
минимальным и максимальным числом участников и
необязательной точкой на карте (широта и долгота). Создатель события становится его организатором.

#### Scenario: Успешное создание

- **GIVEN** вошедший пользователь «Анна»
- **WHEN** Анна создаёт событие «Настолки в антикафе» с интересом «Настольные игры», городом «Санкт-Петербург», адресом
  «Невский пр., 28», началом завтра в 19:00, окончанием в 22:00, сроком регистрации в 17:00, минимумом 3 и максимумом 6
- **THEN** система создаёт событие, указывает Анну организатором и возвращает событие с одним участником

#### Scenario: Создание без точки на карте

- **WHEN** вошедший пользователь создаёт корректное событие без широты и долготы
- **THEN** система создаёт событие без точки на карте

### Requirement: Проверка полей события

Система ДОЛЖНА (SHALL) отклонять событие, если название пустое или длиннее 100 символов, описание длиннее 2000 символов,
интереса нет в справочнике, город или адрес пустые либо у точки на карте указана только одна координата или координата
вне допустимого диапазона.

#### Scenario: Пустое название

- **WHEN** вошедший пользователь создаёт событие с пустым названием
- **THEN** система отклоняет его с ошибкой валидации, указывающей на поле названия

#### Scenario: Неизвестный интерес

- **WHEN** вошедший пользователь создаёт событие с идентификатором интереса, которого нет в справочнике
- **THEN** система отклоняет его с ошибкой валидации, указывающей на поле интереса

#### Scenario: Широта без долготы

- **WHEN** вошедший пользователь создаёт событие с широтой 59.93 и без долготы
- **THEN** система отклоняет его с ошибкой валидации, указывающей на точку на карте

### Requirement: Время события и срок регистрации

Система ДОЛЖНА (SHALL) требовать при создании `now < registrationClosesAt <= startsAt < endsAt`.
Все три даты обязательны и ДОЛЖНЫ (SHALL) содержать смещение часового пояса. Срок регистрации задаётся организатором;
сервер НЕ ДОЛЖЕН (MUST NOT) автоматически подменять его временем начала.

#### Scenario: Закрытие раньше начала

- **WHEN** организатор задаёт начало завтра в 19:00, окончание в 22:00 и срок регистрации в 17:00
- **THEN** сервер сохраняет именно 17:00 как срок закрытия набора

#### Scenario: Закрытие одновременно с началом

- **WHEN** организатор создаёт событие с будущими `registrationClosesAt == startsAt` и более поздним `endsAt`
- **THEN** сервер принимает событие

#### Scenario: Срок регистрации отсутствует

- **WHEN** запрос создания не содержит `registrationClosesAt`
- **THEN** сервер отвечает 400 с ошибкой этого поля

#### Scenario: Срок регистрации уже наступил

- **WHEN** организатор задаёт `registrationClosesAt <= now`, в том числе ровно текущее серверное время
- **THEN** сервер отвечает 400 с ошибкой срока регистрации

#### Scenario: Срок регистрации позже начала

- **WHEN** организатор задаёт `registrationClosesAt > startsAt`
- **THEN** сервер отвечает 400 с ошибкой срока регистрации

#### Scenario: Время начала в прошлом

- **WHEN** организатор задаёт начало не позже текущего серверного времени
- **THEN** сервер отклоняет событие с ошибкой валидации времени

#### Scenario: Окончание не позже начала

- **WHEN** организатор задаёт `endsAt <= startsAt`
- **THEN** сервер отвечает 400 с ошибкой времени окончания

### Requirement: Изменение срока регистрации

Только организатор ДОЛЖЕН (SHALL) иметь возможность изменить `registrationClosesAt` через PATCH до истечения
текущего срока и в состоянии `recruiting`. Новый срок ДОЛЖЕН (SHALL) удовлетворять `now < registrationClosesAt <= startsAt`.
Изменение НЕ ДОЛЖНО (MUST NOT) менять время начала, окончания или место встречи либо переоткрывать закрытый набор.

#### Scenario: Организатор переносит срок

- **GIVEN** событие начинается в 19:00, текущий срок регистрации — 17:00, сейчас 16:00 и состояние `recruiting`
- **WHEN** организатор переносит срок на 18:00
- **THEN** новый срок — 18:00, начало, окончание, место и состав участников сохраняются

#### Scenario: Перенос после закрытия

- **GIVEN** текущий срок регистрации наступил, минимум набран, событие ещё не началось
- **WHEN** организатор пытается продлить регистрацию
- **THEN** сервер отвечает 409 REGISTRATION_CLOSED и не переоткрывает набор

#### Scenario: Чужое событие

- **WHEN** пользователь пытается изменить срок регистрации события другого организатора
- **THEN** сервер отвечает 403

### Requirement: Лимиты участников

Система ДОЛЖНА (SHALL) требовать, чтобы лимиты удовлетворяли условию 1 <= минимум <= максимум <= 50.

#### Scenario: Минимум больше максимума

- **WHEN** вошедший пользователь создаёт событие с минимумом 5 и максимумом 3
- **THEN** система отклоняет его с ошибкой валидации, указывающей на лимиты участников

#### Scenario: Минимум равен нулю

- **WHEN** вошедший пользователь создаёт событие с минимумом 0
- **THEN** система отклоняет его с ошибкой валидации, указывающей на лимиты участников

#### Scenario: Максимум выше потолка

- **WHEN** вошедший пользователь создаёт событие с максимумом 51
- **THEN** система отклоняет его с ошибкой валидации, указывающей на лимиты участников

#### Scenario: Событие для одного

- **WHEN** вошедший пользователь создаёт событие с минимумом 1 и максимумом 1
- **THEN** система создаёт событие, и оно сразу заполнено

### Requirement: Отмена события

Система ДОЛЖНА (SHALL) позволять организатору отменить своё событие в `recruiting` или `registration_closed` до его начала. Отменённое событие остаётся доступно
в карточке в состоянии `cancelled_by_organizer`, и отмену НЕЛЬЗЯ (MUST NOT) вернуть.

#### Scenario: Организатор отменяет предстоящее событие

- **GIVEN** предстоящее событие, организованное Анной
- **WHEN** Анна отменяет его
- **THEN** состояние события становится `cancelled_by_organizer`

#### Scenario: Отмена после закрытия регистрации

- **GIVEN** срок регистрации наступил, минимум набран, состояние `registration_closed`, начало ещё впереди
- **WHEN** организатор отменяет событие
- **THEN** состояние меняется на `cancelled_by_organizer`, состав участников сохраняется

#### Scenario: Отменить пытается кто-то другой

- **GIVEN** предстоящее событие, организованное Анной
- **WHEN** другой вошедший пользователь пытается его отменить
- **THEN** система отклоняет запрос с ошибкой «доступ запрещён»

#### Scenario: Отмена уже начавшегося события

- **GIVEN** событие, организованное Анной, время начала которого прошло
- **WHEN** Анна пытается его отменить
- **THEN** система отклоняет запрос с ошибкой конфликта о том, что событие уже началось

#### Scenario: Повторная отмена

- **GIVEN** отменённое событие, организованное Анной
- **WHEN** Анна пытается отменить его ещё раз
- **THEN** система отклоняет запрос с ошибкой конфликта о том, что событие уже отменено

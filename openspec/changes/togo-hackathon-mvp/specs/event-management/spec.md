# Spec Delta

## Purpose

Позволяет вошедшему пользователю организовать встречу: создать событие со временем, местом и лимитами участников,
изменить его до закрытия набора и при необходимости отменить.

## ADDED Requirements

### Requirement: Создание события

Система ДОЛЖНА (SHALL) позволять вошедшему пользователю создать событие через `POST /api/v1/events` с названием,
описанием, местом `location`, временем начала и окончания, сроком регистрации, лимитами участников, необязательной
иконкой, ровно одной категорией из справочника и необязательной точкой на карте (`latitude` и `longitude`).

#### Scenario: Успешное создание

- **GIVEN** вошедший пользователь «Анна»
- **WHEN** Анна создаёт событие «Вечер настолок» с описанием «Играем в Каркассон» в категории «Настолки» с местом
  «Кафе на Центральной улице, 10»,
  началом завтра в 18:00, окончанием в 21:00, сроком регистрации в 15:00, минимумом 3 и максимумом 6
- **THEN** сервер отвечает 201, в событии организатор Анна, `participantsCount` 1, `availableSlots` 5,
  `isOrganizer` и `isParticipant` равны true

#### Scenario: Создание без точки на карте

- **WHEN** вошедший пользователь создаёт корректное событие без широты и долготы
- **THEN** сервер создаёт событие, `latitude` и `longitude` в ответе равны null

#### Scenario: Пустая иконка

- **WHEN** вошедший пользователь создаёт событие с `icon` в виде пустой строки
- **THEN** сервер создаёт событие, `icon` в ответе равен null

### Requirement: Результат создания события

Сервер ДОЛЖЕН (SHALL) назначить новому событию UUID, организатора из авторизации и состояние `recruiting`, создать
событие, участие организатора и связи категорий в одной транзакции и ответить 201 с заголовком `Location`.

#### Scenario: Ответ содержит адрес события

- **WHEN** вошедший пользователь создаёт корректное событие
- **THEN** сервер отвечает 201 с заголовком `Location` вида `/api/v1/events/{eventId}` и состоянием `recruiting`

### Requirement: Выбор необязательной точки на карте

Клиент ДОЛЖЕН (SHALL) позволять пользователю вручную ввести место и отдельно выбрать точку на карте. Выбранную точку
ДОЛЖНО (SHALL) быть возможно изменить или очистить. При отправке формы клиент ДОЛЖЕН (SHALL) передавать обе координаты
выбранной точки либо не передавать координаты, если точка не выбрана.

#### Scenario: Пользователь выбирает и меняет точку

- **WHEN** пользователь нажимает на карту, а затем выбирает другую точку
- **THEN** клиент показывает маркер в последней выбранной точке и при отправке передаёт её широту и долготу

#### Scenario: Пользователь очищает точку

- **GIVEN** пользователь выбрал точку на карте
- **WHEN** он очищает её
- **THEN** маркер исчезает, а при отправке формы координаты не передаются

#### Scenario: Пользователь вводит только место

- **WHEN** пользователь вводит место вручную и не выбирает точку
- **THEN** клиент позволяет отправить корректную форму без координат

### Requirement: Адрес по точке на карте

При выборе точки клиент ДОЛЖЕН (SHALL) подставлять в поле места адрес, найденный обратным геокодированием Geoapify
через бэкенд; пользователь может его исправить. Контракт геокодирования и поведение при отсутствии результата требуют
согласования.

#### Scenario: Адрес подставляется по точке

- **WHEN** пользователь выбирает на карте точку на Невском проспекте, 28
- **THEN** поле места заполняется адресом «Невский проспект, 28», который можно отредактировать

### Requirement: Проверка полей события

Сервер ДОЛЖЕН (SHALL) отвечать 400 VALIDATION_ERROR с именами полей в `details`, если название, описание или место
отсутствуют, пусты либо состоят из пробелов, название длиннее 100 символов, описание длиннее 500 символов,
`categoryIds` пуст или содержит больше одной категории, у точки на карте указана только одна координата, широта вне `[-90, 90]` или долгота вне `[-180, 180]`,
а также при неизвестных полях запроса. Неизвестная категория ДОЛЖНА (SHALL) отклоняться с 400 CATEGORY_NOT_FOUND.

#### Scenario: Пустое название

- **WHEN** вошедший пользователь создаёт событие с названием из одних пробелов
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `title`

#### Scenario: Слишком длинное название

- **WHEN** вошедший пользователь создаёт событие с названием из 101 символа
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `title`

#### Scenario: Описание отсутствует

- **WHEN** вошедший пользователь создаёт событие без описания
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `description`

#### Scenario: Слишком длинное описание

- **WHEN** вошедший пользователь создаёт событие с описанием из 501 символа
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `description`

#### Scenario: Две категории

- **WHEN** вошедший пользователь создаёт событие с категориями «Кино» и «Кафе/Ресторан»
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `categoryIds`

#### Scenario: Неизвестная категория

- **WHEN** вошедший пользователь создаёт событие с идентификатором категории, которого нет в справочнике
- **THEN** сервер отвечает 400 CATEGORY_NOT_FOUND с полем `categoryIds[0]`

#### Scenario: Широта без долготы

- **WHEN** вошедший пользователь создаёт событие с широтой 59.93 и без долготы
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `longitude`

#### Scenario: Неизвестное поле

- **WHEN** запрос создания содержит поле `organizerId`
- **THEN** сервер отвечает 400 VALIDATION_ERROR

### Requirement: Время события и срок регистрации

Сервер ДОЛЖЕН (SHALL) требовать при создании `now < registrationClosesAt <= startsAt < endsAt` и `startsAt` не позже
чем через один календарный месяц от текущего серверного времени.
Все три даты обязательны и ДОЛЖНЫ (SHALL) содержать смещение часового пояса; сервер возвращает их в UTC.
Срок регистрации задаётся организатором; сервер НЕ ДОЛЖЕН (MUST NOT) автоматически подменять его временем начала.

#### Scenario: Закрытие раньше начала

- **WHEN** организатор задаёт начало завтра в 19:00, окончание в 22:00 и срок регистрации в 17:00
- **THEN** сервер сохраняет именно 17:00 как срок закрытия набора

#### Scenario: Закрытие одновременно с началом

- **WHEN** организатор создаёт событие с будущими `registrationClosesAt == startsAt` и более поздним `endsAt`
- **THEN** сервер принимает событие

#### Scenario: Срок регистрации отсутствует

- **WHEN** запрос создания не содержит `registrationClosesAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Срок регистрации уже наступил

- **WHEN** организатор задаёт `registrationClosesAt <= now`, в том числе ровно текущее серверное время
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Срок регистрации позже начала

- **WHEN** организатор задаёт `registrationClosesAt > startsAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Начало дальше месяца

- **WHEN** 10 ноября организатор задаёт начало 11 декабря
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `startsAt`

#### Scenario: Окончание не позже начала

- **WHEN** организатор задаёт `endsAt <= startsAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `endsAt`

### Requirement: Лимиты участников

Сервер ДОЛЖЕН (SHALL) требовать `1 <= minUsers <= maxUsers <= 50` при создании и для результата изменения.

#### Scenario: Минимум больше максимума

- **WHEN** вошедший пользователь создаёт событие с минимумом 5 и максимумом 3
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `minUsers`

#### Scenario: Минимум равен нулю

- **WHEN** вошедший пользователь создаёт событие с минимумом 0
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `minUsers`

#### Scenario: Максимум выше потолка

- **WHEN** вошедший пользователь создаёт событие с максимумом 51
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `maxUsers`

#### Scenario: Событие для одного

- **WHEN** вошедший пользователь создаёт событие с минимумом 1 и максимумом 1
- **THEN** сервер создаёт событие с `availableSlots` 0 в состоянии `recruiting`

### Requirement: Изменение события

Только организатор ДОЛЖЕН (SHALL) иметь возможность изменить событие через `PATCH /api/v1/events/{eventId}`
в состоянии `recruiting` до текущего `registrationClosesAt`, под блокировкой события. Менять можно `title`,
`description`, `icon`, `minUsers`, `maxUsers`, `categoryIds` и `registrationClosesAt`. Новый срок регистрации
ДОЛЖЕН (SHALL) удовлетворять `now < registrationClosesAt <= startsAt`. `startsAt`, `endsAt`, `location`, координаты,
организатор и состояние НЕ ДОЛЖНЫ (MUST NOT) меняться.

#### Scenario: Организатор переносит срок

- **GIVEN** событие начинается в 19:00, текущий срок регистрации — 17:00, сейчас 16:00 и состояние `recruiting`
- **WHEN** организатор переносит срок на 18:00
- **THEN** новый срок — 18:00, начало, окончание, место и состав участников сохраняются

#### Scenario: Максимум меньше числа участников

- **GIVEN** в событии 4 участника
- **WHEN** организатор уменьшает `maxUsers` до 3
- **THEN** сервер отвечает 409 CAPACITY_BELOW_PARTICIPANTS

#### Scenario: Изменение после закрытия

- **GIVEN** текущий срок регистрации наступил, минимум набран, событие ещё не началось
- **WHEN** организатор пытается продлить регистрацию
- **THEN** сервер отвечает 409 REGISTRATION_CLOSED и не переоткрывает набор

#### Scenario: Изменение отменённого события

- **GIVEN** событие в состоянии `cancelled_by_organizer`
- **WHEN** организатор пытается изменить название
- **THEN** сервер отвечает 409 INVALID_EVENT_STATE

#### Scenario: Чужое событие

- **WHEN** пользователь пытается изменить событие другого организатора
- **THEN** сервер отвечает 403 FORBIDDEN

### Requirement: Частичное изменение

`PATCH` ДОЛЖЕН (SHALL) заменять только переданные поля и сохранять остальные. Пустой объект и null НЕ ДОЛЖНЫ (MUST NOT)
приниматься. `categoryIds` заменяет категорию и содержит ровно одну, пустая строка `icon` удаляет иконку. Описание
НЕ ДОЛЖНО (MUST NOT) становиться пустым или длиннее 500 символов.

#### Scenario: Организатор меняет название и категории

- **WHEN** организатор передаёт новое название и `categoryIds` с другой категорией
- **THEN** сервер возвращает событие с новым названием и ровно этой категорией, остальные поля сохраняются

#### Scenario: Пустое описание при изменении

- **WHEN** организатор передаёт `description` в виде пустой строки
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `description`

#### Scenario: Пустая иконка удаляет иконку

- **WHEN** организатор передаёт `icon` в виде пустой строки
- **THEN** сервер возвращает событие с `icon`, равным null

#### Scenario: Пустое изменение

- **WHEN** организатор отправляет пустой объект или поле со значением null
- **THEN** сервер отвечает 400 VALIDATION_ERROR

### Requirement: Отмена события

Система ДОЛЖНА (SHALL) позволять организатору отменить своё событие через `POST /api/v1/events/{eventId}/cancel`
в `recruiting` или `registration_closed` до `startsAt`. Отменённое событие и его участники сохраняются в состоянии
`cancelled_by_organizer`, и отмену НЕЛЬЗЯ (MUST NOT) вернуть. Повторная отмена уже `cancelled_by_organizer` ДОЛЖНА (SHALL)
возвращать 200 без изменений, в том числе после `startsAt`.

#### Scenario: Организатор отменяет предстоящее событие

- **GIVEN** предстоящее событие в `recruiting`, организованное Анной
- **WHEN** Анна отменяет его
- **THEN** сервер отвечает 200, состояние события становится `cancelled_by_organizer`

#### Scenario: Отмена после закрытия регистрации

- **GIVEN** срок регистрации наступил, минимум набран, состояние `registration_closed`, начало ещё впереди
- **WHEN** организатор отменяет событие
- **THEN** состояние меняется на `cancelled_by_organizer`, состав участников сохраняется

#### Scenario: Отменить пытается кто-то другой

- **GIVEN** предстоящее событие, организованное Анной
- **WHEN** другой вошедший пользователь пытается его отменить
- **THEN** сервер отвечает 403 FORBIDDEN

#### Scenario: Отмена уже начавшегося события

- **GIVEN** событие в `registration_closed`, время начала которого прошло
- **WHEN** организатор пытается его отменить
- **THEN** сервер отвечает 409 INVALID_EVENT_STATE

#### Scenario: Отмена события, отменённого системой

- **GIVEN** событие в `cancelled_by_system`
- **WHEN** организатор пытается его отменить
- **THEN** сервер отвечает 409 INVALID_EVENT_STATE

#### Scenario: Повторная отмена

- **GIVEN** событие, отменённое Анной
- **WHEN** Анна отменяет его ещё раз
- **THEN** сервер отвечает 200, событие не меняется

### Requirement: Обязательные поля формы создания

Клиент ДОЛЖЕН (SHALL) считать обязательными все поля формы, кроме иконки и точки на карте. Если обязательное поле
не заполнено, клиент НЕ ДОЛЖЕН (MUST NOT) отправлять запрос и ДОЛЖЕН (SHALL) показать под кнопкой создания красную
надпись «Пожалуйста, заполните обязательные поля». После создания клиент ДОЛЖЕН (SHALL) показать новое событие
в ленте со счётчиком участников из ответа, равным 1.

#### Scenario: Не заполнено обязательное поле

- **GIVEN** пользователь заполнил форму, кроме места
- **WHEN** он нажимает «Создать встречу»
- **THEN** запрос не отправляется, под кнопкой появляется красная надпись «Пожалуйста, заполните обязательные поля»

#### Scenario: Событие создано

- **WHEN** пользователь отправляет корректную форму
- **THEN** сервер отвечает 201, клиент показывает новую карточку в ленте с одним участником

### Requirement: Ввод полей формы создания

Клиент ДОЛЖЕН (SHALL) предлагать одну категорию из справочника `GET /api/v1/categories`. Календарь даты ДОЛЖЕН (SHALL)
запрещать дни раньше текущего и позже чем через месяц, время выбирается часами и минутами. Поля лимитов ДОЛЖНЫ (SHALL)
принимать только цифры, минимум не меньше 1. Поле описания ДОЛЖНО (SHALL) ограничивать ввод 500 символами.

#### Scenario: Дата за пределами месяца

- **WHEN** пользователь открывает календарь даты
- **THEN** прошедшие дни и дни позже чем через месяц недоступны для выбора

#### Scenario: Нулевой минимум

- **WHEN** пользователь вводит минимум 0 или букву в поле лимита
- **THEN** клиент не принимает значение и не отправляет форму

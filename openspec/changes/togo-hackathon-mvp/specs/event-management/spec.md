# Spec Delta

## Purpose

Позволяет вошедшему пользователю организовать встречу: выбрать категории из справочника, создать событие со временем,
местом и лимитами участников, изменить его до срока регистрации и при необходимости отменить.

## ADDED Requirements

### Requirement: Справочник категорий

Система ДОЛЖНА (SHALL) предоставлять пользователю с действующим токеном полный справочник категорий с идентификатором
и названием, отсортированный по названию и идентификатору. Справочник ведёт бэкенд; клиент НЕ ДОЛЖЕН (MUST NOT)
иметь возможности создавать категории.

#### Scenario: Клиент загружает справочник

- **GIVEN** в справочнике есть категории «Спорт», «Кино» и «Настолки»
- **WHEN** пользователь запрашивает категории с действующим токеном
- **THEN** система возвращает все три категории с идентификаторами в порядке «Кино», «Настолки», «Спорт»

#### Scenario: Справочник без токена

- **WHEN** клиент запрашивает категории без действующего токена
- **THEN** сервер отвечает 401 UNAUTHORIZED

### Requirement: Создание события

Система ДОЛЖНА (SHALL) позволять вошедшему пользователю создать событие с названием, необязательным описанием,
местом, необязательной текстовой иконкой, одной или несколькими категориями из справочника, временем начала и окончания,
сроком регистрации `registrationClosesAt`, минимальным и максимальным числом участников.

#### Scenario: Успешное создание

- **GIVEN** вошедший пользователь «Анна»
- **WHEN** Анна создаёт событие «Настолки в антикафе» с категорией «Настолки», местом «Невский пр., 28», иконкой «🎲»,
  началом завтра в 19:00, окончанием в 22:00, сроком регистрации в 17:00, минимумом 3 и максимумом 6
- **THEN** система отвечает 201, указывает Анну организатором и возвращает событие с одним участником и пятью
  свободными местами

#### Scenario: Создание без описания и иконки

- **WHEN** вошедший пользователь создаёт корректное событие без описания и иконки
- **THEN** система создаёт событие с пустым описанием и `icon: null`

### Requirement: Результат создания события

Сервер ДОЛЖЕН (SHALL) назначать идентификатор, организатора по авторизации и состояние `recruiting`, создавать событие,
участие организатора и связи категорий в одной транзакции и отвечать 201 с заголовком `Location`.

#### Scenario: Адрес созданного события

- **WHEN** вошедший пользователь создаёт корректное событие
- **THEN** сервер отвечает 201 с заголовком `Location` вида `/api/v1/events/{eventId}` и состоянием `recruiting`

#### Scenario: Повторный запрос создаёт новое событие

- **WHEN** вошедший пользователь дважды отправляет одинаковый корректный запрос создания
- **THEN** система создаёт два разных события

### Requirement: Проверка полей события

Система ДОЛЖНА (SHALL) отклонять создание с ошибкой 400, если название или место не содержат ни одного непробельного
символа, список категорий пуст, в запросе есть неизвестные поля либо обязательное поле отсутствует. Повторы в списке
категорий ДОЛЖНЫ (SHALL) объединяться без ошибки.
Неизвестная категория ДОЛЖНА (SHALL) давать 400 CATEGORY_NOT_FOUND, остальные ошибки — 400 VALIDATION_ERROR с именем
поля в `details`.

#### Scenario: Пустое название

- **WHEN** вошедший пользователь создаёт событие с названием из одних пробелов
- **THEN** система отвечает 400 VALIDATION_ERROR с полем `title`

#### Scenario: Неизвестная категория

- **WHEN** вошедший пользователь создаёт событие с идентификатором категории, которого нет в справочнике
- **THEN** система отвечает 400 CATEGORY_NOT_FOUND с полем `categoryIds[0]`, событие не создаётся

#### Scenario: Неизвестное поле

- **WHEN** вошедший пользователь создаёт событие с лишним полем `city`
- **THEN** система отвечает 400 VALIDATION_ERROR

### Requirement: Время события и срок регистрации

Система ДОЛЖНА (SHALL) требовать при создании `now < registrationClosesAt <= startsAt < endsAt`.
Все три даты обязательны и ДОЛЖНЫ (SHALL) содержать смещение часового пояса. Срок регистрации задаётся организатором;
сервер НЕ ДОЛЖЕН (MUST NOT) автоматически подменять его временем начала. Сервер ДОЛЖЕН (SHALL) возвращать даты в UTC.

#### Scenario: Закрытие раньше начала

- **WHEN** организатор задаёт начало завтра в 19:00, окончание в 22:00 и срок регистрации в 17:00
- **THEN** сервер сохраняет именно 17:00 как срок закрытия набора

#### Scenario: Закрытие одновременно с началом

- **WHEN** организатор создаёт событие с будущими `registrationClosesAt == startsAt` и более поздним `endsAt`
- **THEN** сервер принимает событие

#### Scenario: Срок регистрации отсутствует

- **WHEN** запрос создания не содержит `registrationClosesAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Срок регистрации уже наступил

- **WHEN** организатор задаёт `registrationClosesAt <= now`, в том числе ровно текущее серверное время
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Срок регистрации позже начала

- **WHEN** организатор задаёт `registrationClosesAt > startsAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `registrationClosesAt`

#### Scenario: Окончание не позже начала

- **WHEN** организатор задаёт `endsAt <= startsAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `endsAt`

#### Scenario: Дата без часового пояса

- **WHEN** организатор передаёт `startsAt` без смещения часового пояса
- **THEN** сервер отвечает 400 VALIDATION_ERROR

### Requirement: Лимиты участников

Система ДОЛЖНА (SHALL) требовать, чтобы лимиты удовлетворяли условию 1 <= minUsers <= maxUsers. Организатор
занимает одно место.

#### Scenario: Минимум больше максимума

- **WHEN** вошедший пользователь создаёт событие с минимумом 5 и максимумом 3
- **THEN** система отвечает 400 VALIDATION_ERROR с полем лимитов участников

#### Scenario: Минимум равен нулю

- **WHEN** вошедший пользователь создаёт событие с минимумом 0
- **THEN** система отвечает 400 VALIDATION_ERROR с полем `minUsers`

#### Scenario: Событие для одного

- **WHEN** вошедший пользователь создаёт событие с минимумом 1 и максимумом 1
- **THEN** система создаёт событие, у него 0 свободных мест и состояние `recruiting`

### Requirement: Изменение события

Только организатор ДОЛЖЕН (SHALL) иметь возможность изменить через PATCH название, описание, иконку, категории,
лимиты и срок регистрации, и только в `recruiting` до текущего `registrationClosesAt`. Новый срок ДОЛЖЕН (SHALL)
удовлетворять `now < registrationClosesAt <= startsAt`, лимиты результата — `1 <= minUsers <= maxUsers`, а `maxUsers`
НЕ ДОЛЖЕН (MUST NOT) становиться меньше числа участников. Изменение НЕ ДОЛЖНО (MUST NOT) переоткрывать закрытый набор.

#### Scenario: Организатор переносит срок

- **GIVEN** событие начинается в 19:00, текущий срок регистрации — 17:00, сейчас 16:00 и состояние `recruiting`
- **WHEN** организатор переносит срок на 18:00
- **THEN** новый срок — 18:00, начало, окончание, место и состав участников сохраняются

#### Scenario: Максимум меньше числа участников

- **GIVEN** у события 4 участника
- **WHEN** организатор уменьшает `maxUsers` до 3
- **THEN** сервер отвечает 409 CAPACITY_BELOW_PARTICIPANTS и не меняет событие

#### Scenario: Изменение после закрытия

- **GIVEN** текущий срок регистрации наступил, минимум набран, событие ещё не началось
- **WHEN** организатор пытается продлить регистрацию
- **THEN** сервер отвечает 409 REGISTRATION_CLOSED и не переоткрывает набор

#### Scenario: Изменение отменённого события

- **GIVEN** событие в `cancelled_by_organizer`
- **WHEN** организатор пытается изменить его название
- **THEN** сервер отвечает 409 INVALID_EVENT_STATE

#### Scenario: Чужое событие

- **WHEN** пользователь пытается изменить событие другого организатора
- **THEN** сервер отвечает 403 FORBIDDEN

### Requirement: Частичное изменение события

При изменении переданные поля ДОЛЖНЫ (SHALL) заменяться, а отсутствующие сохраняться. Пустой объект, null и
неизвестные поля, включая `startsAt`, `endsAt` и `location`, ДОЛЖНЫ (SHALL) давать 400 VALIDATION_ERROR. Пустая строка
`icon` удаляет иконку, пустая строка `description` очищает описание, `categoryIds` полностью заменяет категории.

#### Scenario: Частичное изменение

- **WHEN** организатор передаёт только новое название
- **THEN** название меняется, остальные поля сохраняются

#### Scenario: Удаление иконки

- **WHEN** организатор передаёт `icon: ""`
- **THEN** в ответе `icon: null`

#### Scenario: Пустое изменение

- **WHEN** организатор отправляет пустой объект
- **THEN** сервер отвечает 400 VALIDATION_ERROR

#### Scenario: Изменение времени начала

- **WHEN** организатор передаёт новое `startsAt`
- **THEN** сервер отвечает 400 VALIDATION_ERROR и не меняет событие

### Requirement: Отмена события

Система ДОЛЖНА (SHALL) позволять организатору отменить своё событие в `recruiting` или `registration_closed` до его
начала. Отменённое событие и его участники сохраняются в состоянии `cancelled_by_organizer`, и отмену НЕЛЬЗЯ (MUST NOT)
вернуть. Повторная отмена события в `cancelled_by_organizer` ДОЛЖНА (SHALL) возвращать 200 без изменений, в том числе
после начала. Отмена в других состояниях или после начала ДОЛЖНА (SHALL) давать 409 INVALID_EVENT_STATE.

#### Scenario: Организатор отменяет предстоящее событие

- **GIVEN** предстоящее событие в `recruiting`, организованное Анной
- **WHEN** Анна отменяет его
- **THEN** состояние события становится `cancelled_by_organizer`

#### Scenario: Отмена после закрытия регистрации

- **GIVEN** срок регистрации наступил, минимум набран, состояние `registration_closed`, начало ещё впереди
- **WHEN** организатор отменяет событие
- **THEN** состояние меняется на `cancelled_by_organizer`, состав участников сохраняется

#### Scenario: Отменить пытается кто-то другой

- **GIVEN** предстоящее событие, организованное Анной
- **WHEN** другой вошедший пользователь пытается его отменить
- **THEN** система отвечает 403 FORBIDDEN

#### Scenario: Отмена уже начавшегося события

- **GIVEN** событие в `registration_closed`, организованное Анной, время начала которого прошло
- **WHEN** Анна пытается его отменить
- **THEN** система отвечает 409 INVALID_EVENT_STATE

#### Scenario: Отмена события, отменённого системой

- **GIVEN** событие в `cancelled_by_system`, организованное Анной
- **WHEN** Анна пытается его отменить
- **THEN** система отвечает 409 INVALID_EVENT_STATE

#### Scenario: Повторная отмена

- **GIVEN** событие в `cancelled_by_organizer`, организованное Анной
- **WHEN** Анна отменяет его ещё раз
- **THEN** система отвечает 200 и возвращает событие без изменений

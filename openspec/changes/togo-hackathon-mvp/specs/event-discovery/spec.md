# Spec Delta

## Purpose

Помогает найти событие, к которому стоит присоединиться: лента событий с фильтрами и страницами, подробная карточка
события и карта событий.

## ADDED Requirements

### Requirement: Лента событий

Система ДОЛЖНА (SHALL) отдавать пользователю с действующим токеном по `GET /api/v1/events` события всех состояний,
включая прошедшие и отменённые, в порядке `startsAt ASC, id ASC`. Состояние каждого события ДОЛЖНО (SHALL) быть
актуализировано по серверному времени до фильтрации.

#### Scenario: Ленте не нужны фильтры

- **GIVEN** событие, которое начнётся завтра, событие, которое началось вчера, и отменённое событие
- **WHEN** клиент запрашивает ленту без параметров
- **THEN** сервер возвращает все три события с их состояниями и `total` 3

#### Scenario: Лента без авторизации

- **WHEN** клиент запрашивает ленту без действующего токена
- **THEN** сервер отвечает 401 UNAUTHORIZED, клиент выполняет предусмотренный вход Mini App

#### Scenario: Порядок ленты

- **GIVEN** событие, которое начнётся через три дня, и событие, которое начнётся завтра
- **WHEN** клиент запрашивает ленту
- **THEN** первым идёт событие, которое начнётся завтра

### Requirement: Страницы ленты

Сервер ДОЛЖЕН (SHALL) возвращать ленту страницей `EventPage`: `limit` по умолчанию 20 и от 1 до 100, `offset`
по умолчанию 0 и не меньше 0. `total` ДОЛЖЕН (SHALL) равняться числу событий после фильтрации до пагинации.

#### Scenario: Страница ленты

- **GIVEN** 25 событий
- **WHEN** клиент запрашивает ленту с `limit=10` и `offset=20`
- **THEN** сервер возвращает 5 событий и `total` 25

#### Scenario: Пустая выдача

- **WHEN** фильтрам не соответствует ни одно событие
- **THEN** сервер отвечает 200 с `items: []` и `total` 0

#### Scenario: Некорректная страница

- **WHEN** клиент передаёт `limit=101` или `offset=-1`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с именем параметра

### Requirement: Экран ленты

Экран ленты клиента ДОЛЖЕН (SHALL) по умолчанию запрашивать события с `startsFrom=now` и показывать состояние
каждого события, в том числе отменённого.

#### Scenario: Экран ленты скрывает прошедшие события

- **GIVEN** событие, которое начнётся завтра, и событие, которое началось вчера
- **WHEN** пользователь открывает экран ленты
- **THEN** клиент показывает только завтрашнее событие

### Requirement: Фильтры ленты

Сервер ДОЛЖЕН (SHALL) сужать ленту по любому сочетанию фильтров, объединённых через AND:
`query` — подстрока названия без учёта регистра, крайние пробелы удаляются, пустая строка не фильтрует;
`categoryId` — события с этой категорией, неизвестный UUID даёт пустую выдачу;
`startsFrom` — включительная нижняя граница начала; `startsTo` — исключительная верхняя граница начала;
`state` — актуальное состояние; `participating=true` — события с участием текущего пользователя.

#### Scenario: Фильтр по категории

- **GIVEN** события с категориями «Спорт» и «Кино»
- **WHEN** клиент фильтрует ленту по категории «Кино»
- **THEN** в ленте только событие с категорией «Кино»

#### Scenario: Поиск по названию не учитывает регистр

- **GIVEN** событие «Вечер НАСТОЛОК»
- **WHEN** клиент передаёт `query` со значением «  настолок »
- **THEN** в ленте есть это событие

#### Scenario: Фильтр по времени

- **GIVEN** события в пятницу 18:00 и в воскресенье 18:00
- **WHEN** клиент передаёт `startsFrom` суббота 00:00 и `startsTo` понедельник 00:00
- **THEN** в ленте только воскресное событие

#### Scenario: Границы диапазона

- **GIVEN** событие начинается ровно в `startsFrom`, другое — ровно в `startsTo`
- **WHEN** клиент запрашивает ленту с этими границами
- **THEN** в ленте только первое событие

#### Scenario: Сочетание фильтров

- **GIVEN** события «Спорт» в `recruiting` и в `cancelled_by_system`
- **WHEN** клиент фильтрует по категории «Спорт» и состоянию `recruiting`
- **THEN** в ленте только событие в `recruiting`

#### Scenario: Начало диапазона не раньше его конца

- **WHEN** клиент передаёт `startsFrom`, не меньший `startsTo`
- **THEN** сервер отвечает 400 VALIDATION_ERROR с полем `startsFrom`

### Requirement: Фильтр свободных мест

При `hasFreePlaces=true` сервер ДОЛЖЕН (SHALL) возвращать только события, к которым можно присоединиться:
`state = recruiting`, `now < registrationClosesAt` и `participantsCount < maxUsers`. Значение false не фильтрует.

#### Scenario: Только события со свободными местами

- **GIVEN** два события в `recruiting` до срока регистрации: одно заполнено, другое имеет свободное место
- **WHEN** клиент передаёт `hasFreePlaces=true`
- **THEN** в ленте только событие со свободным местом

#### Scenario: Место есть, но регистрация закрыта

- **GIVEN** у будущего события есть свободные места, но `registrationClosesAt` уже наступил, а фоновая обработка ещё
  не обновила состояние
- **WHEN** клиент передаёт `hasFreePlaces=true`
- **THEN** событие не попадает в выдачу

### Requirement: Карточка события

Система ДОЛЖНА (SHALL) отдавать пользователю с действующим токеном по `GET /api/v1/events/{eventId}` любое событие,
включая прошедшие и отменённые: название, описание, место, точку на карте, время начала и окончания,
`registrationClosesAt`, актуальное состояние, иконку, лимиты, организатора, категории, `participantsCount`,
`availableSlots`, `isParticipant` и `isOrganizer`. Состав участников доступен отдельным запросом.

#### Scenario: Пользователь открывает карточку

- **GIVEN** событие «Вечер настолок» с максимумом 6 и 4 участниками, организованное Анной
- **WHEN** пользователь открывает его карточку
- **THEN** в карточке все поля события, организатор Анна, `participantsCount` 4 и `availableSlots` 2

#### Scenario: Закрытая регистрация до начала встречи

- **GIVEN** событие ещё не началось, срок регистрации наступил, минимум набран, а фоновая обработка задержалась
- **WHEN** пользователь открывает карточку
- **THEN** сервер возвращает `registration_closed`, клиент показывает срок регистрации и скрывает кнопки вступления
  и выхода

#### Scenario: Неизвестное событие

- **WHEN** пользователь открывает карточку с неизвестным идентификатором события
- **THEN** сервер отвечает 404 EVENT_NOT_FOUND

#### Scenario: Некорректный идентификатор

- **WHEN** пользователь запрашивает событие с идентификатором, который не является UUID
- **THEN** сервер отвечает 400 VALIDATION_ERROR

### Requirement: События на карте

Клиент ДОЛЖЕН (SHALL) показывать отфильтрованную ленту на карте: ставить маркер для каждого события с точкой на карте и
пропускать события без неё. Выбор маркера ДОЛЖЕН (SHALL) открывать карточку этого события.

#### Scenario: Карта показывает события с точкой

- **GIVEN** два предстоящих события, одно с точкой на карте, другое без
- **WHEN** пользователь открывает карту
- **THEN** на карте один маркер, для события с точкой

#### Scenario: Маркер ведёт к карточке

- **WHEN** пользователь выбирает маркер на карте
- **THEN** клиент открывает карточку этого события

# Spec Delta

## Purpose

Обеспечивает автоматический вход в ToGo при открытии Telegram Mini App, проверку данных запуска и доступ к API
по токену приложения без формы логина, отдельной регистрации и выбора демо-пользователя.

## ADDED Requirements

### Requirement: Автоматический вход Telegram Mini App

Клиент ДОЛЖЕН (SHALL) при открытии внутри Telegram автоматически передать исходную строку `Telegram.WebApp.initData`
в `POST /api/v1/auth/telegram`. Клиент НЕ ДОЛЖЕН (MUST NOT) показывать форму логина, Telegram Login Widget или
выбор демо-пользователя. При отсутствии данных запуска клиент ДОЛЖЕН (SHALL) предложить открыть приложение в Telegram.

#### Scenario: Запуск внутри Telegram

- **GIVEN** Mini App открыта внутри Telegram и получила `initData`
- **WHEN** клиент запускается
- **THEN** клиент автоматически выполняет вход, получает токен и открывает приложение без формы логина

#### Scenario: Запуск без данных Telegram

- **GIVEN** пользователь открыл URL в обычном браузере без `initData`
- **WHEN** клиент запускается
- **THEN** клиент показывает сообщение об открытии через Telegram и не предлагает вход по логину или демо-вход

### Requirement: Учётная запись по проверенному пользователю Telegram

Система ДОЛЖНА (SHALL) находить или создавать учётную запись по Telegram ID из проверенных данных запуска и хранить
в ней `tgId` и `tgLogin`. При повторном входе система НЕ ДОЛЖНА (MUST NOT) создавать дубликат. `tgLogin` ДОЛЖЕН
(SHALL) обновляться из проверенного username при каждом входе и становиться null, если username отсутствует.
Ответ входа ДОЛЖЕН (SHALL) быть одинаковым для нового и существующего пользователя.

#### Scenario: Первый вход

- **GIVEN** пользователя с Telegram ID 123456789 ещё нет
- **WHEN** сервер получает корректные `initData` с этим ID и username «anna_s»
- **THEN** сервер создаёт одну учётную запись с `tgId` 123456789 и `tgLogin` «anna_s» и выдаёт токен приложения

#### Scenario: Повторный вход

- **GIVEN** пользователь с Telegram ID 123456789 уже входил с username «anna_s»
- **WHEN** сервер получает свежие корректные `initData` с тем же Telegram ID и username «anna_smirnova»
- **THEN** сервер выдаёт токен для той же учётной записи, дубликат не создаётся, `tgLogin` равен «anna_smirnova»

#### Scenario: Пользователь без username

- **WHEN** сервер получает корректные `initData` пользователя без username
- **THEN** вход разрешён, `tgLogin` равен null, идентичность определяется Telegram ID

### Requirement: Проверка подписи и свежести initData

Система ДОЛЖНА (SHALL) проверять подпись Mini App и `auth_date`. При недействительной подписи, возрасте данных
более 5 минут, времени более чем на 30 секунд в будущем или отсутствии подписанного `user` вход ДОЛЖЕН (SHALL)
завершаться 401 без создания пользователя и выдачи токена. Неподписанные поля и `initDataUnsafe` НЕ ДОЛЖНЫ (MUST NOT)
использоваться для установления личности.

#### Scenario: Подделанный пользователь

- **WHEN** клиент отправляет `initData`, в которых Telegram ID изменён после подписи
- **THEN** сервер отвечает 401 INVALID_TELEGRAM_INIT_DATA, пользователь не создаётся

#### Scenario: Нет подписи или пользователя

- **WHEN** клиент отправляет строку `initData` без `hash` или без подписанного `user`
- **THEN** сервер отвечает 401 INVALID_TELEGRAM_INIT_DATA и не выдаёт токен

#### Scenario: Устаревшие данные

- **WHEN** клиент отправляет правильно подписанные `initData` возрастом 5 минут и 1 секунда
- **THEN** сервер отвечает 401 INVALID_TELEGRAM_INIT_DATA

#### Scenario: Данные из будущего

- **WHEN** клиент отправляет правильно подписанные данные с `auth_date` на 31 секунду позже серверного времени
- **THEN** сервер отвечает 401 INVALID_TELEGRAM_INIT_DATA

#### Scenario: Допустимые границы времени

- **WHEN** возраст правильно подписанных данных равен ровно 5 минутам либо время выдачи опережает сервер ровно на 30 секунд
- **THEN** проверка свежести проходит

### Requirement: Токен приложения

После успешного входа система ДОЛЖНА (SHALL) вернуть `accessToken`, `tokenType: Bearer`, `expiresIn: 3600` и `user`.
Клиент ДОЛЖЕН (SHALL) передавать токен в `Authorization` при последующих запросах. Сервер ДОЛЖЕН (SHALL)
проверять его подлинность и срок действия. Токены и исходные `initData` НЕ ДОЛЖНЫ (MUST NOT) попадать в логи.

#### Scenario: Авторизованный запрос

- **GIVEN** клиент получил действующий токен
- **WHEN** он передаёт `Authorization: Bearer <accessToken>`
- **THEN** сервер выполняет запрос от имени пользователя, которому выдан токен, с проверкой прав на действие

#### Scenario: Подделанный или истёкший токен

- **WHEN** клиент передаёт изменённый токен или токен, срок действия которого истёк
- **THEN** сервер отвечает 401 UNAUTHORIZED и не выполняет защищённое действие

### Requirement: Окончание и восстановление сессии Mini App

Клиент ДОЛЖЕН (SHALL) хранить access token в памяти и удалять его после 401. После перезагрузки вход повторяется
по ещё свежим `initData`. Если они устарели, клиент ДОЛЖЕН (SHALL) предложить переоткрыть Mini App без формы логина
и бесконечных повторов. Автоматическое продление через refresh token и серверный logout в текущий контракт не входят.

#### Scenario: Перезагрузка со свежими данными

- **GIVEN** клиент перезагрузился и `initData` ещё проходят проверку свежести
- **WHEN** клиент повторяет автоматический вход
- **THEN** он получает новый токен той же учётной записи без формы логина

#### Scenario: Токен истёк после часа работы

- **GIVEN** access token истёк и исходные `initData` старше 5 минут
- **WHEN** API отвечает 401
- **THEN** клиент очищает токен, останавливает защищённые действия и предлагает переоткрыть Mini App

### Requirement: Текущий пользователь

Система ДОЛЖНА (SHALL) возвращать по `GET /api/v1/users/me` данные текущего пользователя согласно `CurrentUser`
из API: UUID в ToGo, `tgId` и необязательный `tgLogin`. Без действующего токена запрос ДОЛЖЕН (SHALL) завершаться 401.

#### Scenario: Получение текущего пользователя

- **GIVEN** клиент успешно прошёл автоматический вход
- **WHEN** он запрашивает `GET /api/v1/users/me` с токеном
- **THEN** сервер возвращает UUID в ToGo, Telegram ID и username либо null

### Requirement: Доступ к API требует токена

Все операции API, кроме `POST /api/v1/auth/telegram`, ДОЛЖНЫ (SHALL) требовать действующий Bearer-токен,
включая ленту, карточку и справочник. Локальные моки и профиль `demo` НЕ ДОЛЖНЫ (MUST NOT) разрешать обход
проверки Telegram на сервере или выдачу токена по произвольно выбранному пользователю.

#### Scenario: Анонимный запрос ленты

- **WHEN** клиент запрашивает ленту без токена
- **THEN** сервер отвечает 401, клиенту требуется автоматический вход через Telegram

#### Scenario: Попытка обойти вход в профиле demo

- **GIVEN** сервер запущен с профилем `demo` для загрузки тестовых данных
- **WHEN** клиент обращается к `/api/v1/auth/demo-users` или `/api/v1/auth/demo-login`
- **THEN** сервер не предоставляет таких операций; токен по выбранному пользователю получить нельзя

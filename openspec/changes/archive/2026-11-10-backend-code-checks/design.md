# Design

## Context

- Бэкенд собирается Maven из `backend/pom.xml` на Spring Boot 4.1.2 и Kotlin 2.2.0. Исходники Kotlin лежат в
  `backend/src/main/kotlin` и `backend/src/test/kotlin`, а `openapi-generator` пишет контроллеры и модели в
  `target/generated-sources/openapi` в пакет `itmo.goto.generated`.
- Тесты используют Testcontainers с PostgreSQL 18, поэтому для `verify` нужен Docker.
- Замер от 10 ноября 2026 года (JaCoCo через командную строку, без `itmo.goto.generated`): 39 из 81 строки (48%) и 20
  из 36 ветвей (56%). Не покрыты заглушки пяти сервисов (20 строк), `model/User.kt` (8 строк), `main` (2 строки) и часть
  ветвей `ApiErrorHandler` (16 из 28) и `ApiFailure` (4 из 8).
- В репозитории нет `.github/` и нет `.editorconfig`. Код уже местами расходится по стилю: `GotoApplication.kt` и часть
  `pom.xml` отформатированы табуляцией.
- Задача 2.5 плана `togo-hackathon-mvp` планирует `.github/workflows/ci.yml` с бэкендом и фронтендом и защиту `main`.
  Это изменение её не трогает.

## Goals / Non-Goals

**Goals:**

- Одинаковые проверки локально и в CI без отдельной настройки CI.
- Порог 80% по строкам и ветвям проходит сразу после подключения, без понижения порога и без исключения рукописного кода.

**Non-Goals:**

- Анализ сгенерированного кода и стиль `pom.xml`, YAML и SQL.
- Публикация отчётов в GitHub Code Scanning, комментарии с покрытием в запросах на слияние и внешние сервисы покрытия.
- Защита ветки `main` и обязательность проверки — это задача 2.5 исходного плана.

## Decisions

### 1. Все проверки живут в Maven `verify`

Kover, detekt и ktlint подключаются плагинами Maven и привязываются к жизненному циклу, а workflow вызывает только
`./backend/mvnw -f backend/pom.xml -B verify`. Так локальный запуск и CI совпадают по составу и настройкам, а команда в
`AGENTS.md` остаётся прежней.

Альтернатива: отдельные шаги в workflow (`detekt-cli`, готовые actions для ktlint). Отвергнута: проверки CI расходятся
с локальными, и нарушение находится только после push.

### 2. Покрытие через Kover

`org.jetbrains.kotlinx:kover-maven-plugin` с целями `instrumentation`, `report-xml`, `report-html` и `verify`. Kover
понимает байткод Kotlin (инлайн-функции, проверки на null, служебные методы), поэтому не засчитывает компилятору лишних
непокрытых ветвей. XML отчёт пишется в формате JaCoCo и читается теми же инструментами.

Правило: группа `APPLICATION`, две границы по `COVERED_PERCENTAGE` с минимумом 80 — для `LINE` и для `BRANCH`. Фильтр
исключает классы `itmo.goto.generated.*` и `itmo.goto.GotoApplicationKt` (обёртка над `main`, которую нельзя вызвать в
тесте без запуска всего приложения). Больше исключений нет.

Агент Kover подключается к Surefire через свойство `argLine`. Если позже в `pom.xml` появится собственный `argLine` у
Surefire, он ДОЛЖЕН включать `@{argLine}`, иначе покрытие станет нулевым.

Альтернатива: JaCoCo. Отвергнута по решению пользователя: Kover точнее считает код Kotlin. Альтернатива: граница
только по строкам. Отвергнута: правила событий в домене ветвистые, и именно ветви там важны.

### 3. Доведение покрытия до порога тестами

- Неиспользуемый `model/User.kt` удаляется: у него нет пакета, его колонки не совпадают с таблицей `users`, а сущность
  пользователя появится с задачами блока 3.
- Каждая заглушка в `itmo.goto.service` получает юнит-тест на метод: вызов бросает `ResponseStatusException` со статусом
  501. Тесты создают сервис напрямую без Spring. Когда метод реализуется, его тест заглушки заменяется тестами
  поведения.
- `ApiErrorHandler` и `ApiFailure` получают сценарии для непокрытых ветвей: каждый код `ApiError.Code` даёт свой статус,
  клиентская ошибка Spring с 4xx и неизвестное исключение с 500, индексы массивов в пути поля. Сценарии добавляются в
  существующие тесты `ApiErrorHandlerTest` и в новый `ApiFailureTest`, `ProbeController` расширяется при необходимости.
- Порядок такой: сначала тесты при выключенной проверке порога, затем включение порога. Так видно, что порог проходит
  на реальном покрытии.

Альтернатива: временно исключить заглушки из расчёта. Отвергнута по решению пользователя: исключения легко забыть снять.

### 4. Статический анализ через detekt

`com.github.ozsie:detekt-maven-plugin` с целью `check` в фазе `verify`. Исходники: `src/main/kotlin` и
`src/test/kotlin`, поэтому сгенерированный код в анализ не попадает. Конфигурация `backend/detekt.yml` строится поверх
стандартной (`buildUponDefaultConfig`), `maxIssues: 0`, без файла baseline. В `detekt.yml` попадают только
обоснованные отступления, каждое с комментарием о причине, например имена тестов в обратных кавычках для `FunctionNaming`
в тестовом коде. Правила форматирования detekt (`detekt-formatting`) не подключаются, чтобы не дублировать ktlint.
Отчёты: HTML и SARIF в `target/detekt`.

Альтернатива: detekt с type resolution через `detekt-cli`. Отложена: плагин Maven анализирует без типов, этого хватает
для старта, а `detekt-cli` усложнит сборку.

### 5. Форматирование через ktlint

`com.github.gantsign.maven:ktlint-maven-plugin` с целью `check` в фазе `verify` для основного и тестового кода.
Стиль задаёт `.editorconfig` в корне репозитория: `ktlint_code_style = intellij_idea`, отступ 4 пробела,
`max_line_length = 120`. Стиль IntelliJ совпадает с форматтером IDE, которым пользуется команда, поэтому
переформатирование в IDE не спорит с проверкой. Автоисправление: `./backend/mvnw -f backend/pom.xml ktlint:format`.
В `.editorconfig` выключено одно правило — `blank-line-between-when-conditions`: оно вставляет пустые строки между
ветками `when`, а соглашение проекта требует тел методов без пустых строк.

Альтернатива: `ktlint_official`. Отвергнута: строже форматтера IDE и даёт постоянные расхождения при автоформатировании.

### 6. Workflow `.github/workflows/backend.yml`

- Триггеры: `pull_request` в любую ветку и `push` в `main`, без фильтра по путям. Фильтр путей экономит минуты, но
  пропущенная обязательная проверка блокирует слияние, когда задача 2.5 включит защиту ветки.
- Одна задача на `ubuntu-latest`: `actions/checkout`, `actions/setup-java` с Temurin 21 и `cache: maven`, затем
  `./backend/mvnw -f backend/pom.xml -B verify`.
- `permissions: contents: read`, секретов нет, поэтому запросы из форков проверяются полностью.
- `concurrency` по ветке с `cancel-in-progress` для запросов на слияние, чтобы новый push отменял устаревший запуск.
- Шаг `actions/upload-artifact` с `if: always()` прикладывает `target/site/kover`, `target/detekt`,
  `target/ktlint*` и `target/surefire-reports`.
- Версии actions фиксируются по мажорной версии.

Задача 2.5 исходного плана затем добавит проверки фронтенда отдельным workflow и сделает задачу `backend` обязательной
для `main`.

## Risks / Trade-offs

- [detekt 1.x собран под Kotlin 2.0 и может не разобрать новый синтаксис Kotlin 2.2] → Взять последнюю стабильную
  версию плагина; если разбор падает, остановиться и обсудить переход на detekt 2 вместо подавления ошибок.
- [Kover для Maven моложе версии для Gradle] → Проверить на первом запуске, что XML отчёт не пустой и что
  падение теста под порогом действительно валит сборку.
- [Тесты заглушек выбрасываются по мере реализации] → Это ожидаемо: каждый реализованный метод получает тесты поведения,
  которые держат покрытие.
- [Порог 80% на ветвях мешает быстрому прототипированию на хакатоне] → Порог не понижается; если он начнёт мешать,
  решение принимает команда явно, а не через исключения.
- [Testcontainers замедляют CI] → Кэш Maven через `setup-java`, общий контейнер в рамках одного запуска уже настроен.

## Migration Plan

Существующих проверок нет. Порядок внедрения: тесты и удаление `User.kt`, затем Kover с порогом, затем ktlint с
исправлением кода, затем detekt с исправлением кода, затем workflow. Откат — удалить плагин из `pom.xml` или workflow.

# Design

## Context

Мотивация — в proposal.md, требования — в `specs/event-ratings/spec.md`.

Изменение опирается на код `togo-hackathon-mvp`:

- Состояния события вычисляет доменный `Meeting.current(now)`; сервисы приводят событие к актуальному состоянию под
  блокировкой строки (`EventRepository.locked`) через `NotificationQueue.settle`, который также ставит уведомления
  о переходах.
- Отказ домена `Refusal` переводится в `ApiError.Code` по имени (`ApiFailure(refusal)`), поэтому у каждого значения
  `Refusal` одно сообщение на код.
- Счётчики профиля считаются `@Formula` в сущности `User`, а не хранятся.
- Карточку события строит `Event.card(viewer, participant)`; лента получает признаки участия одним запросом
  `participations.joined(...)` на страницу.
- Фронтенд берёт типы из `src/common/api/schema.ts`, который генерирует `npm run api:generate` из `api/openapi.yaml`.
- Последняя миграция — `V4__comment_notifications.sql`.

## Goals / Non-Goals

**Goals:**

- Хранить только сами оценки, а средние значения вычислять запросом, чтобы они не расходились с данными.
- Сохранить контракт аддитивным: новые поля необязательны, существующие коды ошибок переиспользуются.

**Non-Goals:**

- Кэширование и денормализация средних: объём данных хакатона их не требует.
- Защита от накрутки помимо правила «оценивает только участник».

## Decisions

### 1. Контракт: отдельный тег и PUT для единственной оценки

`PUT /api/v1/events/{eventId}/rating` с телом `RateEventRequest { score }` (`integer`, `minimum: 1`, `maximum: 5`,
`additionalProperties: false`) отвечает `EventResponse`. PUT выбран потому, что у пользователя ровно одна оценка на
событие по адресу события. По аналитике (раздел 8) оценку нельзя изменить: повторный запрос отклоняется
с 409 ALREADY_RATED, новым значением перечня `ApiError.code`. Отдельный тег `Ratings` даёт
генератору интерфейс `RatingsApiService`, который реализует новый `RatingsService`, как `CommentsService`
реализует `CommentsApiService`.

Новая схема `Rating { average: number (double, 0..5), count: integer (int32, >= 0) }`. Поля `Event.rating` и
`Event.myRating` (`integer`, 1..5) объявлены `nullable: true`; `CurrentUser.organizerRating` и
`UserProfile.organizerRating` всегда заданы и без оценок равны `{ average: 0.0, count: 0 }`, как требует аналитика.
Новые поля не входят в `required`, поэтому старые клиенты их не замечают. Остальные отказы используют существующие
коды 403 FORBIDDEN, 409 INVALID_EVENT_STATE, 400 VALIDATION_ERROR и 404 EVENT_NOT_FOUND.
Чтобы дробная оценка давала 400, а не обрезалась до целого, `application.properties` выключает
`spring.jackson.deserialization.accept-float-as-int`; это так же делает строгими остальные целые поля контракта.

Альтернатива: `POST` на коллекцию оценок. Отвергнута: у пользователя одна оценка на событие, и адрес события её
однозначно задаёт.

### 2. Модель данных: одна таблица оценок

Миграция `V5__event_ratings.sql`:

```
event_ratings(id uuid default uuidv7(), event_id → events, user_id → users,
              score smallint, created_at timestamptz, updated_at timestamptz)
unique (event_id, user_id)
check (score between 1 and 5)
```

Уникальность по паре даёт правило «одна оценка на участника» и индекс для выборки по событию. Отдельный индекс для
рейтинга организатора не нужен: запрос идёт от `events(organizer_id)`, индекс которого уже есть, к уникальному индексу
`event_ratings(event_id, user_id)`. База не проверяет, что оценивает не организатор и что событие завершено: это
правила домена и сервиса, как и остальные правила событий.

Запись — нативный `INSERT` после проверки, что оценки ещё нет. Проверка идёт под блокировкой строки события, поэтому
два параллельных нажатия одного пользователя сериализуются, и второе получает ALREADY_RATED; уникальность пары
страхует от обхода сервиса. Колонка `updated_at` остаётся равной `created_at`, потому что оценка не меняется.

### 3. Правило оценки в домене, проверка роли в сервисе

`Meeting.rate(now): Decision` приводит встречу к актуальному состоянию и принимает оценку только в `FINISHED`, иначе
возвращает `Refused(this, INVALID_EVENT_STATE)`. Так правило «оценивается только завершённое событие» и запоздавший
фоновый переход покрываются юнит-тестами без базы, как `join` и `cancel`. Двенадцатый метод `Meeting` превышает
порог detekt `TooManyFunctions`, поэтому `detekt.yml` поднимает `thresholdInClasses` до 12 с комментарием: все правила
события остаются в одном доменном объекте по решению 4 изменения `togo-hackathon-mvp`.

Роль проверяет сервис, как `CommentsService` проверяет участие: посторонний и организатор получают
`ApiFailure(FORBIDDEN, ...)` со своими сообщениями «Оценить событие могут только его участники» и «Организатор не может
оценить своё событие». Причина: `Refusal.FORBIDDEN` несёт сообщение «Действие доступно только организатору события»,
а перевод отказа в код идёт по имени, поэтому второе сообщение для того же кода через домен не выразить без
изменения общего механизма.

Порядок в `RatingsService.rateEvent` в одной транзакции:

1. `events.locked(id)` или 404 EVENT_NOT_FOUND;
2. `notifications.settle(event, event.meeting().current(now), now)` — актуальное состояние сохраняется до любых
   отказов, а переход в `finished` ставит уведомления так же, как при чтении карточки;
3. роль из `event.role(user, participations.existsByEventIdAndUserId(...))`: не `PARTICIPANT` — 403;
4. `meeting.rate(now)`: отказ — 409 после сохранения состояния, как требует решение 6 изменения
   `togo-hackathon-mvp`;
5. оценка этого пользователя уже есть — 409 ALREADY_RATED;
6. запись оценки и ответ `event.card(...)` с новой оценкой.

Шаги живут в `RatingsService.rate(eventId, user, score)`; `rateEvent` берёт пользователя из `Identity`, а webhook бота —
по Telegram ID нажавшего, поэтому оба пути подчиняются одним правилам.

Блокировка строки события нужна только для согласованной актуализации состояния с другими операциями; сама оценка
состав не меняет. Порядок блокировок «событие, затем пользователь» сохраняется: строка пользователя не блокируется.

Альтернатива: новое значение `Refusal` для роли при оценке. Отвергнута: значения `Refusal` названы по кодам контракта,
а нового кода изменение не вводит.

### 4. Средние считаются запросом

Средняя оценка события — два `@Formula` в `Event`: `round(avg(score), 1)` и `count(*)` по `event_ratings` этого
события. Рейтинг организатора — два `@Formula` в `User` по `event_ratings` с `JOIN events ON organizer_id`, по образцу
`created` и `visited`. Для события пустой `avg` даёт `null`, и `rating` в ответе `null`; для организатора
`coalesce(..., 0)` даёт 0.0, и `organizerRating` всегда задан. Аналитика предлагает хранить `users.rating` и
пересчитывать его при каждой оценке; запрос даёт то же наблюдаемое значение без риска расхождения, как и счётчики
профиля в решении 7 изменения `togo-hackathon-mvp`.
Округление до одного знака делает PostgreSQL, поэтому сервер и тесты видят одно и то же число.

`myRating` зависит от зрителя, поэтому не формула: `card` получает оценку зрителя аргументом. Лента загружает оценки
зрителя одним запросом на страницу (`participations.scores(user, eventIds)`), как сейчас загружает признаки участия,
а карточка, вступление, изменение и отмена — запросом `participations.score(event, user)`; создание передаёт `null`,
потому что у нового события оценок нет. Запросы лежат в `ParticipationRepository` рядом с `joined`, а не
в `RatingRepository`: иначе конструкторы `EventDiscoveryService` и `EventParticipationService` получили бы седьмую
зависимость и нарушили порог detekt `LongParameterList`. `RatingRepository` держит только запись оценки.

Альтернатива: хранить `rating_sum` и `rating_count` в `events` и `users`. Отвергнута: счётчики обновлялись бы при каждой
оценке и её замене и могли разойтись с таблицей, а выигрыша на объёме демо нет. Это то же решение, что для счётчиков
профиля в решении 7 изменения `togo-hackathon-mvp`.

### 5. Фронтенд

Тип `Rating` и новые поля приходят из `npm run api:generate`. В модуле `Events` новый компонент `EventRating` в
`EventDetail`: средняя оценка с числом оценок, если `rating` задан, и пять звёзд для участника не организатора при
`state === 'finished'`, пока `myRating` равен `null`; после оценки звёзды показывают `myRating` и не нажимаются. Выбор звезды отправляет `PUT` через TanStack Query и заменяет событие в кэше ответом сервера,
поэтому средняя оценка обновляется без повторного запроса. Ошибка показывается сообщением из `ApiError`, как в форме
комментариев. В модуле `Profile` `UserProfile` показывает под фото звезду с `organizerRating.average`, 0.0 без
оценок, и число созданных событий. Модули
по-прежнему импортируют друг друга только через `index.ts`.

### 6. Оценка кнопками бота

Переход события в `finished` в `NotificationQueue.settle` ставит уведомление вида `rating` каждому участнику, кроме
организатора; уникальность `(user_id, event_id, kind)` очереди исключает повторы. Миграция `V6` добавляет вид в CHECK.
Доставка отправляет `sendMessage` с одним рядом из пяти кнопок `N ⭐` и `callback_data` `rate:<eventId>:<N>` (43 байта
при пределе Telegram 64).

Нажатие приходит в тот же webhook как `callback_query`. `BotService` проверяет секрет, разбирает данные строгим
шаблоном, находит пользователя по `from.id` и вызывает `RatingsService.rate` в отдельной транзакции. После неё бот
отвечает `answerCallbackQuery` («Оценка принята» или сообщение отказа), при успехе присылает благодарность из аналитики
и снимает кнопки `editMessageReplyMarkup` с пустой клавиатурой; при ALREADY_RATED тоже снимает кнопки, потому что
Telegram не умеет делать их неактивными. Ошибки Bot API при ответе гасятся: webhook отвечает 204, иначе Telegram
повторит обновление. Webhook должен получать `callback_query`: если у бота задан `allowed_updates`, в него нужно
добавить этот тип.

Альтернатива: кнопка `web_app`, открывающая карточку события для оценки в Mini App. Отвергнута: аналитика требует
оценку прямо в сообщении бота.

## Risks / Trade-offs

- [Формулы средних выполняются на каждое событие ленты] → На странице из 12–20 событий это 12–20 подзапросов по
  уникальному индексу; при росте данных можно перейти к денормализации из альтернативы решения 4.
- [Генератор `kotlin-spring` может сделать необязательные поля DTO обязательными аргументами конструктора] → Сразу
  после правки контракта собрать `./backend/mvnw -f backend/pom.xml compile` и подставить `null` в местах, где
  строятся `Card`, `CurrentUser` и `UserProfile`.
- [Оценки нельзя изменить или удалить, а встреча с тремя участниками даёт заметный вес одной оценке] → Принять
  по аналитике; показ числа оценок рядом со средним даёт пользователю контекст.
- [Пользователь нажал кнопку, а ответ Bot API не дошёл] → Оценка уже сохранена; кнопки останутся, но повторное нажатие
  получит «Вы уже оценили это событие» и снимет их.
- [Состояние `finished` наступает только после `endsAt`, а фоновая задача может запаздывать] → Сервис оценки
  актуализирует событие сам (решение 3), поэтому кнопка работает сразу после окончания встречи.

## Migration Plan

Миграции `V5` и `V6` только добавляют таблицу и вид уведомления, поэтому существующие данные не меняются, и откат
образа на предыдущий SHA оставляет лишнее, но безвредное. Перед выкаткой проверить `getWebhookInfo` бота: если
`allowed_updates` не пуст и не содержит `callback_query`, заново вызвать `setWebhook` с этим типом. Новые поля API необязательны, поэтому старая сборка фронтенда работает
с новым бэкендом.

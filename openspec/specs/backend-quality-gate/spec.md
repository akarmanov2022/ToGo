# backend-quality-gate Specification

## Purpose

Не даёт непроверенному коду бэкенда попасть в `main`: одна команда сборки локально и в GitHub Actions запускает тесты,
проверяет покрытие, статический анализ и форматирование Kotlin.

## Requirements

### Requirement: Единая команда проверки

Полная проверка бэкенда ДОЛЖНА (SHALL) запускаться одной командой `./backend/mvnw -f backend/pom.xml verify` из корня
репозитория и завершаться ненулевым кодом, если упал хотя бы один тест, порог покрытия, статический анализ или проверка
форматирования. Локальный запуск и запуск в CI ДОЛЖНЫ (SHALL) выполнять одни и те же проверки с одними и теми же
настройками.

#### Scenario: Чистый код проходит проверку

- **WHEN** разработчик запускает `verify` на коде, где все тесты зелёные, покрытие не ниже порога и нет нарушений
  анализаторов
- **THEN** команда завершается с кодом 0

#### Scenario: Упавший тест останавливает проверку

- **WHEN** один из тестов бэкенда падает
- **THEN** `verify` завершается с ненулевым кодом и называет упавший тест

### Requirement: Порог покрытия

Проверка ДОЛЖНА (SHALL) измерять покрытие рукописного кода из `backend/src/main` всеми тестами модуля и падать, если
покрытие по строкам или по ветвям ниже 80%. Из расчёта ДОЛЖНЫ (SHALL) исключаться только код, сгенерированный из
`api/openapi.yaml`, и точка входа приложения. Проверка ДОЛЖНА (SHALL) оставлять HTML и XML отчёт покрытия.

#### Scenario: Покрытие ниже порога

- **WHEN** в основной код добавлен класс без тестов, и покрытие по строкам опускается ниже 80%
- **THEN** `verify` завершается с ненулевым кодом и сообщает фактическое и требуемое покрытие

#### Scenario: Непокрытые ветви при покрытых строках

- **WHEN** все строки покрыты, но покрытие по ветвям ниже 80%
- **THEN** `verify` завершается с ненулевым кодом

#### Scenario: Сгенерированный код не влияет на покрытие

- **WHEN** в контракт добавлен новый эндпоинт, и генератор создал для него непокрытые контроллер и модели
- **THEN** покрытие рукописного кода не меняется

### Requirement: Статический анализ Kotlin

Проверка ДОЛЖНА (SHALL) анализировать основной и тестовый код Kotlin на запахи, сложность и потенциальные ошибки и
падать при любом найденном нарушении. Прощённых заранее нарушений НЕ ДОЛЖНО (SHALL NOT) быть, а сгенерированный код НЕ
ДОЛЖЕН (SHALL NOT) анализироваться. Проверка ДОЛЖНА (SHALL) оставлять отчёт с файлом, строкой и правилом.

#### Scenario: Запах кода в запросе на слияние

- **WHEN** в основной код добавлен метод, нарушающий правило анализатора, например с неиспользуемым приватным членом
- **THEN** `verify` завершается с ненулевым кодом, а отчёт называет файл, строку и правило

#### Scenario: Нарушение в тестах

- **WHEN** нарушение правила анализатора добавлено в тестовый код
- **THEN** `verify` завершается с ненулевым кодом

### Requirement: Форматирование Kotlin

Проверка ДОЛЖНА (SHALL) сверять форматирование основного и тестового кода Kotlin с единым стилем репозитория и падать
при любом отклонении. Разработчику ДОЛЖНА (SHALL) быть доступна команда, которая исправляет форматирование
автоматически.

#### Scenario: Неотформатированный файл

- **WHEN** в файл Kotlin добавлен отступ табуляцией или лишний пробел
- **THEN** `verify` завершается с ненулевым кодом и называет файл и строку

#### Scenario: Автоисправление

- **WHEN** разработчик запускает команду автоисправления на неотформатированном коде
- **THEN** следующий `verify` не находит нарушений форматирования

### Requirement: Проверка в GitHub Actions

Workflow GitHub Actions ДОЛЖЕН (SHALL) запускать полную проверку бэкенда на каждый запрос на слияние в любую ветку и на
каждый push в `main`, отмечая запуск красным при её провале. Отчёты покрытия, анализаторов и тестов ДОЛЖНЫ (SHALL)
прикладываться к запуску как артефакты и при успехе, и при провале. Workflow НЕ ДОЛЖЕН (SHALL NOT) требовать секретов.

#### Scenario: Запрос на слияние с нарушением

- **WHEN** открыт запрос на слияние, в котором покрытие ниже порога или есть нарушение анализатора
- **THEN** проверка бэкенда в запросе отмечена красным, а отчёты доступны в артефактах запуска

#### Scenario: Зелёный запрос на слияние

- **WHEN** открыт запрос на слияние, проходящий все проверки
- **THEN** проверка бэкенда в запросе отмечена зелёной

#### Scenario: Push в main

- **WHEN** коммит попадает в `main`
- **THEN** workflow выполняет ту же проверку на этом коммите

#### Scenario: Запрос на слияние из форка

- **WHEN** запрос на слияние открыт из форка без доступа к секретам репозитория
- **THEN** проверка выполняется полностью, так как секреты ей не нужны
